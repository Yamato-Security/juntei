# YARAスキャン

`yara-scan` は、収集済みファイルの内容をYARAルールで検索するコマンドです。
Rust製の [Boreal](https://github.com/vthib/boreal) を使用し、Windows、macOS、Linuxで動作します。
ファイルはデータとして読み取り、実行しません。Defenderから復元した `.quarantined` ファイルも対象になります。
`auto-parse` とは独立したコマンドで、通常のアーティファクト解析時には自動実行しません。

## ルールの選択

`--rules` を指定しない場合、[YARA Forge](https://github.com/YARAHQ/yara-forge) の
GitHubリリースからHTTPSでパッケージをダウンロードし、コンパイルしてスキャンします。

| パッケージ | 指定方法 | 用途 |
|---|---|---|
| Core | 既定値、または `--ruleset core` | 精度と性能を重視した比較的絞られたルールです。まずはこちらから開始してください。 |
| Extended | `--ruleset extended` | 検索対象を広げたハンティングです。追加の検知を文脈と照合してください。 |
| Full | `--ruleset full` | 最も広い対象範囲です。リソース消費と誤検知の可能性が増えます。 |

```bash
juntei yara-scan -d evidence/ -o yara-core/
juntei yara-scan -d evidence/ --ruleset extended -o yara-extended/
juntei yara-scan -d evidence/ --ruleset full -o yara-full/ -t jsonl
```

オンライン実行では毎回、既定で最新パッケージをダウンロードします。
特定のリリースに固定するには `--rules-release YYYYMMDD` を使います。
例：そのリリースが公開されていれば `--rules-release 20261115` です。
`Rules.yar` と `Summary.json` を保管すれば、`latest` の内容が変わっても、
保存されたソースとSHA256で使用ルールを特定できます。

オフラインではルールファイル、または `.yar` / `.yara` を含むディレクトリを指定します。

```bash
juntei yara-scan -d evidence/ --rules local-rules/ -o yara-offline/
juntei yara-scan -f recovered/agent.exe.quarantined --rules local.yar -o yara-file/
```

`--rules` を使うとネットワーク通信を行いません。明示的な `--ruleset` や `--rules-release` との併用はできません。
ディレクトリは再帰的に探索し、同じ名前空間内でパス順に読み込みます。依存関係には `include` を使います。
`include` は記述ファイルを基準に解決し、指定したディレクトリ内
（ファイルを指定した場合はその親ディレクトリ内）に限定します。同じファイルは一度だけ展開します。
循環参照、範囲外の参照、ルール名の重複、未対応モジュールはエラーになります。
不正なルールを黙って除外しません。ローカルルールはUTF-8で保存してください。

コンパイル警告は `CompilationWarnings.txt` に保存します。
コンパイル段階で失敗した場合は `CompilationError.txt` に内容を記録します。
`Rules.yar` は、ローカルルールを展開したスナップショット、またはダウンロードした元のソースです。
ルールのライセンスは各作者のものが適用され、ダウンロードによって変更されません。

## 対象範囲と制限

拡張子にかかわらず通常ファイルを対象とします。シンボリックリンクや特殊ファイルは追跡せず、
スキップとして記録します。証拠ディレクトリ内にある使用中のルールソースも自己検知を防ぐため除外します。
出力先は証拠の外側にある**新しいディレクトリ**を指定し、ローカルルールを上書きしないでください。
単一ファイルのスキャンでは、そのファイルと同じ親ディレクトリ内に新しい結果ディレクトリを作成できます。
証拠の内容は変更しません。

ファイル全体を通常の**ファイル用セマンティクス**で評価します。プロセスメモリ用の評価ではありません。
ZIPやディスクイメージの展開、非レジデントデータの復元、実行中プロセスのメモリスキャンは行いません。
VHDX/E01をそのまま指定して内部のファイルがスキャンされると考えず、取り出したファイルを指定してください。
MFTメタデータから作った空のプレースホルダーには、マルウェア本体のバイト列は含まれません。

| オプション | 既定値 | 内容 |
|---|---|---|
| `-d, --directory <DIR>` | `-f` とどちらか必須 | ディレクトリを再帰スキャンします。 |
| `-f, --file <FILE>` | `-d` とどちらか必須 | 単一ファイルをスキャンします。 |
| `-o, --output <DIR>` | 必須 | 新規出力ディレクトリ。 |
| `-r, --rules <PATH>` | なし | オフライン用のルールファイル／ディレクトリ。 |
| `--ruleset core\|extended\|full` | `core` | ダウンロードするパッケージ。 |
| `--rules-release <RELEASE>` | `latest` | `latest` または `YYYYMMDD`。 |
| `-t, --output-type csv\|jsonl` | `csv` | 検知と対象範囲レポートの形式。 |
| `-T, --threads <N>` | CPU数、最大8 | 並列ファイルスキャン数。指定範囲は1～256です。 |
| `--timeout <SECONDS>` | 60 | ファイルごとのYARA評価上限秒数。読み取り時間は含みません。 |
| `--max-file-mib <MIB>` | 無制限 | MFTを含む全ファイルに適用する任意のMiB上限。 |
| `--max-mft-mib <MIB>` | 共通上限を継承 | MFTに限って上書きする任意のMiB上限。 |
| `--computer <NAME>` | 近傍の `client_info.json`、不明なら空欄 | 証拠ホスト名を明示します。 |
| `-q, --quiet` | 無効 | ロゴ、進捗、通常の準備メッセージを省略します。 |
| `-K, --no-color` | 無効 | 色を無効化します。 |

コンパイル済みルールはワーカー間で共有します。各ワーカーはファイルを読み取り専用でメモリにマップし、
そのマッピングからハッシュ計算とスキャンを行うため、ファイルをメモリにコピーしません。メモリ使用量は
ファイルサイズや並列数に比例せず、OS はスキャンが通過したページを順次解放できます。
通常ファイルにも MFT にも**既定のファイルサイズ上限はありません**。任意の `--max-file-mib` と
`--max-mft-mib` はスキャン時間を抑える上限であり、メモリ上限ではありません。ハッシュとスキャンは同じ
マッピングから行い、スキャン中にサイズや更新日時の変化を検出した場合は読み取りエラーとして報告します。
安定した証拠コピーを使い、スキャン中に他のプロセスがファイルを切り詰めないようにしてください。
入出力エラーは未完了として報告し、正常なスキャンとしては扱いません。

Ctrl+Cはファイル間でキャンセルを要求します。実行中の評価は設定したタイムアウトまで続く場合があります。
キャンセル対象は `Cancelled` として記録します。

## 出力

| ファイル | 内容 |
|---|---|
| `YaraDetections.csv` / `.jsonl` | ルールとファイルの組み合わせごとの検知。未完了スキャンの途中結果も含みます。 |
| `YaraFiles.csv` / `.jsonl` | 発見したファイル、スキップ対象、ディレクトリ探索エラーごとの対象範囲。一致した、またはスキャンできなかった MFT のレジデントストリームの行も含みます。 |
| `Summary.json` | 完了状態、件数、設定、ルール／パッケージのハッシュ、ソース一覧、エンジンの版。 |
| `Rules.yar` | 再現用の使用ルール。 |
| `CompilationWarnings.txt` | コンパイル警告。空の場合もあります。 |
| `RunStarted.json` | 開始時の記録。`Summary.json` がなければ実行は正常完了していません。 |

証拠パスは入力ディレクトリからの相対パスです。単一ファイルでは親ディレクトリからの相対パスになります。
`Computer` は近傍の `client_info.json` または `--computer` から取得し、不明なら空欄にします。
解析用コンピューターの名前を証拠ホスト名として使いません。

### 検知フィールド

| フィールド | 解釈 |
|---|---|
| `Computer` | 判明した場合の証拠ホスト名。 |
| `FilePath` | ソースの相対パス。`.quarantined` も保持します。 |
| `Size` | スキャンしたバイト数。 |
| `SHA256` | スキャンした同じバイト列のハッシュ。 |
| `ScanStatus` | 評価完了は `Scanned`、未完了の途中結果は `ScanError` です。 |
| `Rule`, `Namespace`, `Tags` | ルール名、名前空間、タグ。 |
| `Metadata` | 作者、説明、参照、重要度などルールに定義されたメタデータのJSON文字列。 |
| `MatchLocations` | 一致パターンごとの最初の位置を最大16パターン記録したJSON文字列。`Offset` はファイル内のバイト位置です。`Length` と `XorKey` も含みます。一致した内容自体は出力しません。 |

### 対象範囲フィールド

`Computer`、`FilePath`、`Size`、`SHA256` で対象を特定します。未読・スキップ対象のハッシュは空欄です。
`Matches` は一致ルール数、`ElapsedMs` は読み取り・ハッシュ・評価の所要時間、`Note` は取得できたエラー説明です。

`Status` は `Scanned`、`SkippedTooLarge`、`SkippedSymlink`、`SkippedSpecialFile`、
`SkippedRuleSource`、`DiscoveryError`、`ReadError`、`ScanError`、`Cancelled` を区別します。
スキップやタイムアウトは**安全を確認した状態ではありません**。途中で検知があっても `ScanError` になる場合があります。
検知件数はルールとファイルの組み合わせ数であり、マルウェアファミリー数や侵害ホスト数ではありません。

終了コードは対象の評価完了が0、対象範囲の未完了が3、準備・出力エラーが2、キャンセルが130です。
検知そのものはエラーではありません。`SkippedRuleSource` だけなら未完了扱いにしません。
まず `Summary.json` を確認し、実行痕跡、ファイルシステム、イベントログと照合して判断してください。
YARAの一致は調査の手がかりであり、一致しないことは安全の証明になりません。

## MFTのスキャンとレジデントファイルの復元

一般的な名前（`$MFT`、末尾が `$MFT`、`%24MFT`、`MFT`、`.mft`）、または妥当な先頭FILEレコードヘッダーからMFTを認識します。
MFTは通常ファイルの後に**一つずつ**、同じコンパイル済みルールで、次の2段階で処理します。

1. 生のバイト列を他のファイルと同じようにマップしてスキャンします。ファイル名、インデックス項目、スラックでの一致は
   `SourceType` が `MFTRaw` の検知行になり、オフセットはMFTを基準とします。
2. すべてのFILEレコードをファイルから1レコードずつ読み取ります。MFT全体のコピーは作りません。NTFS更新シーケンスの
   fixupが正しいレコードごとに、各レジデント `$DATA` ストリームを独立したファイルとしてスキャンします。これにより
   `filesize`、ヘッダー判定、複合条件はMFTではなくそのファイルを対象とします。この段階は1段階目に依存しません。
   小さいPEファイルだけを対象にするルールのように、MFT全体には決して一致しないルールでも、本来の対象である
   レジデントファイルを見つけられます。

**単独でルールに一致したレジデントストリームだけ**を `RecoveredMFT/` に `.quarantined` 拡張子で保存します。
保存名には元のファイル名、レコード番号、シーケンス番号、属性識別情報を含めますが、証拠側のディレクトリ構成は再作成しません。
元の証拠は変更しません。名前付き代替ストリームと削除レコードも対象になります。
拡張レコードの所有者は、世代番号とベースレコードの属性リストの両方を検証できた場合にだけ記録します。
非レジデントの内容はボリュームのデータクラスタにあり、単独のMFTからは復元できません。その数は `Summary.json` に
記録し、空の代替ファイルは作りません。未使用（ゼロ埋め）のレコードスロットは数えます。署名、サイズ、fixupが
不正なレコードは `InvalidRecord` として報告し、内容を確認できなかったため対象範囲は未完了になります。

任意の `--max-file-mib` 上限は全ファイルに適用し、`--max-mft-mib` を指定するとMFTだけ上書きします。
正の整数MiBで、64ビットのバイト数に収まる範囲を指定できます。上限でスキップしたMFTはどちらの段階も行いません。
`--max-mft-recoveries <N>` は実行全体で実際に保存するストリーム数の上限です。既定は **1000**、指定範囲は1～100000です。
上限を超えて一致したストリームも検知行には残し、状態を `RecoveryLimitReached` にして、実行を未完了として扱います。
画面・検知行に表示する16パターンの上限は復元に影響しません。

```bash
juntei yara-scan -d evidence/ --ruleset full -o yara-mft/
```

MFTが見つかると `YaraMFTResults.csv` または `YaraMFTResults.jsonl` を追加します。復元したストリーム、一致したが
保存しなかったストリーム、評価に失敗したストリーム、破損レコード（先頭100件。残りは件数のみ）ごとに1行です。

| フィールド | 意味 |
|---|---|
| `Computer`, `MFTPath` | 証拠ホスト名と相対MFTパス。 |
| `EntryNum`, `SN` | 物理FILEレコードの番号と世代番号。 |
| `BaseEntryNum`, `BaseSN` | 検証できた拡張レコードのベース所有者。不明なら空欄です。 |
| `OriginalPath`, `Stream` | 解決できたWindowsパスと名前付きストリーム。未解決のパスは明示します。 |
| `AttributeID`, `AttributeOffset` | 属性のインスタンス番号とレコード内オフセット。 |
| `Deleted` | 物理FILEレコードが未割り当てかどうか。 |
| `Rules` | ストリーム単独で一致したルール名。 |
| `Status`, `Note` | 復元状態と説明。 |
| `Size`, `SHA256` | fixup適用後の正確なレジデント内容のサイズとハッシュ。 |
| `RecoveredFile` | 出力ディレクトリからの相対復元パス。未保存なら空欄です。 |

状態は `Recovered`、`RecoveryLimitReached`、`StreamScanError`、`InvalidMFT`、`InvalidRecord`、
`AttributeError`、`TruncatedTail`、`Cancelled` を区別します。スキャンエラー、破損レコード、復元上限は
対象範囲を未完了にします。`TruncatedTail` は最後の完全なレコードより後ろのバイトを記録するだけで、
その部分は1段階目で既にスキャンしています。

通常の検知・対象範囲テーブルには `SourceType` を追加し、`File`、`MFTRaw`、`MFTResident` を区別します。
レジデント行の `FilePath` はレコードとストリームを指す仮想参照で、追加の入力ファイルではありません。
検知行の `RecoveredFile` が実際の復元先を示します。生データの一致オフセットはMFTを基準とし、
レジデント行はそのストリームを基準とします。両方の一致が同じ証拠を指す場合もあり、検知数はマルウェアの一意数ではありません。
`Summary.json` には実際のMFT上限、MFT専用の上書き指定、レコード統計（読み取ったレコード数、未使用・破損レコード数、
レジデント・非レジデントストリーム数、復元ファイル数）を記録します。サイズ上限のnullは無制限を示します。

保存されたファイルは**YARAに一致した証拠**であり、マルウェア判定や実行の証明ではありません。
