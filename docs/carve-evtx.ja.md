# イベントログのカービング

`carve-evtx` は、ログの消去や削除のあとに残った Windows イベントログ（EVTX）のチャンクや、
Windows がページファイルやメモリに残したチャンクを復元し、Hayabusa やイベント ビューアーで開ける
通常の `.evtx` ファイルとして書き出します。

EVTX ファイルは 4 KiB のファイルヘッダーと、それに続く 64 KiB のチャンクでできています。各チャンクは
独自の文字列テーブルとテンプレートテーブルを持っているため、ログの残りの部分がなくてもレコードを
読めます。ログが消去または削除されても、クラスターが再利用されるまでチャンクはディスクに残るのが
普通です。また、Windows は開いているログのチャンクをメモリに保持し、メモリのページは
`pagefile.sys` に書き出されます。

## 使い方

```bash
juntei carve-evtx -f host.E01 -o carved/
juntei carve-evtx -f host.vhdx --free-space-only -o carved-free/
juntei carve-evtx -f pagefile.sys --live-logs evidence/C/Windows/System32/winevt/Logs/ -o carved-pagefile/
juntei carve-evtx -f memory.raw -o carved-memory/ -t jsonl
juntei carve-evtx -f host.E01
```

| オプション | 意味 |
|---|---|
| `-f, --file <FILE>` | 入力です。E01 または VHDX のディスクイメージ、RAW のディスクまたはボリューム、`pagefile.sys`、RAW のメモリイメージ、その他の任意のファイルを指定できます。 |
| `-l, --live-logs <DIR>` | 現行の `.evtx` ログ（再帰的に検索します）です。これらのログにあるレコードは書き出しません。コレクションの `winevt\Logs` の横にあるページファイルなど、NTFS のない入力に使います。ディスクイメージでは、ボリューム上の現行ログを自動で見つけます。 |
| `--no-file-system` | NTFS ボリュームがあっても、入力を単なるバイト列として読みます。 |
| `--cluster-size <BYTES>` | NTFS ボリュームのない入力で、NTFS 圧縮されたチャンクに使うクラスターサイズです。512、1024、2048、4096（既定値）のいずれかです。 |
| `--free-space-only` | NTFS ボリュームの空きクラスターだけを検索します。速くなりますが、ページファイル、シャドウコピーのストアファイル、その他のファイルは検索しません。 |
| `--keep-live` | 現行ログのチャンクと、レコードがまだ現行ログにあるチャンクも書き出します。 |
| `-o, --output <DIR>` | 復元したログ、復元したファイル、レポートを保存する、新しいディレクトリまたは空のディレクトリです。指定しない場合は、サマリーだけを表示します。 |
| `-t, --output-type <TYPE>` | チャンクとレコードのレポートの形式で、`csv`（既定値）または `jsonl` です。 |

検索が完了した場合（チャンクが見つからなかった場合を含みます）、終了コードは 0 です。エラーの場合は
1 です。

## チャンクの見つけ方

1. **シグネチャの検索。** 入力を 4 MiB ずつ読み、`ElfChnk\0` をすべてのバイトオフセットで検索します。
   空き領域、ページファイル、メモリにあるチャンクは境界にそろっていないためです。
2. **ヘッダーの確認。** ヘッダーがもっともらしい場合にチャンクとして受け入れます。ヘッダーサイズが
   128 であること、レコード番号とレコード ID が順序どおりで、チャンクに収まる数より少ないこと、
   最後のレコードと空き領域のオフセットがチャンクの中にあることを確認します。空ページ（レコードなしで
   書かれたチャンク）も、古いレコードが残っていることがあるため受け入れます。
3. **チェックサム。** ヘッダーとレコードのチェックサムを計算してチャンクのレポートに記録しますが、
   一致を条件にはしません。一部が上書きされたチャンクにも、読めるレコードが残っているためです。
4. **NTFS 圧縮。** シグネチャの位置のバイト列がもっともらしいチャンクでない場合は、NTFS 圧縮を
   試します。NTFS はファイルを 16 クラスターの単位で圧縮し、単位の中の 4 KiB ごとに別々に圧縮します
   （LZNT1）。そのため、4 KiB のブロックの先頭から始まるチャンクでは、シグネチャがリテラルのバイトの
   まま残ります。単位を展開し、次の単位は次のクラスターから読みます。圧縮できなかった単位はそのまま
   保存され、ゼロだけの単位にはクラスターがまったく割り当てられません。そこで、チャンクの末尾について
   展開したデータとゼロの両方を試し、レコードのチェックサムが一致する方、またはレコードがよりよく
   読める方を採用します。ディスクイメージでは、ボリュームのクラスターサイズとクラスターの区切りを
   使います。その他のファイルでは、`--cluster-size` がクラスターサイズを指定し、区切りはバイト 0 から
   始まります。
5. **レコード。** レコードは、ヘッダーの終わりから、ヘッダーにある最後のレコードのオフセットまで、
   サイズをたどって読みます。シグネチャ、サイズ、末尾にあるサイズのコピーが一致するレコードを有効と
   します。実際のチャンクには最後のレコードと同じ ID を持つ前のレコードがあり得るため、レコード ID で
   読み取りを止めることはありません。壊れたレコードのあとは、次の有効なレコードから読み続けます。
   空き領域のオフセットより後ろのスラックにある古いレコード（および空ページのすべてのレコード）は、
   スラックのレコードとして一覧にします。
6. **詳細。** 割り当て済みの各レコードのチャネル、プロバイダー、コンピューター、イベント ID は、evtx
   クレートで読みます。チャンクのチャネルは、そのレコードで最も多いチャネルです。割り当て済みの
   レコードがない空ページでは、チャンクがあったログの名前がわかれば、その名前からチャネルを決めます。

## ディスクイメージと NTFS ボリューム

E01 または VHDX のイメージ、あるいは NTFS ファイルシステムを持つ RAW のディスクまたはボリューム
（MBR または GPT のディスク、またはパーティションのないボリューム）では、各 NTFS ボリュームの
`$Boot`、`$Bitmap`、`$MFT` を読み、各チャンクをそのクラスターによって分類します。

| 場所 | 意味 |
|---|---|
| `FreeSpace` | どのファイルも使っていないクラスターです。 |
| `DeletedLog` | 削除されたログの `$MFT` レコードがまだ指している空きクラスター、またはそのようなクラスターから復元したログです。 |
| `LiveLog` | 使用中のイベントログのクラスターです。`--keep-live` を指定しない限り書き出しません。 |
| `AllocatedFile` | `pagefile.sys`、`System Volume Information` にあるシャドウコピーのストアファイル、コピーされたログなど、他のファイルのクラスターです。`Owner` にそのパス（とストリーム）を示します。 |
| `AllocatedUnknown` | どの `$MFT` レコードも指していない、割り当て済みのクラスター（ファイルシステムのメタデータまたは破損）です。 |
| `OutsideVolumes` | ディスク上のどの NTFS ボリュームの外側でもあります。 |
| `Unclassified` | ページファイルやメモリイメージなど、入力に NTFS ボリュームがありません。 |

**削除されたログ。** `$MFT` レコードがまだ読め、空きクラスターだけを指している削除済みの `.evtx` は、
NTFS 圧縮されたログも含めて検索の前にまるごと復元し、`Recovered/Volume<N>/<path>` に保存します。
そのチャンクは他のチャンクと同じように扱い、検索で見つかった同じチャンクは重複になります。一部の
クラスターが再利用されていた場合、データランが他の `$MFT` レコードに続いている場合、4 GiB を超える
場合は、削除されたログを復元しません。残っているチャンクは検索で見つかります。

**現行ログ。** 現行ログはファイルシステムを通して読みます（圧縮されている場合は展開します）。その
チャンクと割り当て済みのレコードが、重複排除の基準になります。現行ログのチャンクのスラックにある
古いレコードは、ログに表示されなくなっているため基準に含めません。

## 重複排除

各チャンクは一度だけ、レコードが増える場合にだけ書き出します。

| ステータス | 意味 |
|---|---|
| `Written` | 復元したログに書き出しました。 |
| `SkippedLiveLog` | 現行ログのクラスターにありました。 |
| `DuplicateOfLiveLog` | 現行ログのチャンクと同一です。 |
| `DuplicateChunk` | 見つかった他のチャンクと同一です。 |
| `RecordsInLiveLogs` | すべてのレコード（割り当て済みとスラック）が現行ログにあります。 |
| `RecordsInOtherChunks` | すべてのレコードが、現行ログか、すでに書き出したチャンクにあります。 |
| `NoRecords` | 有効なレコードがまったくありません。 |

レコードは、そのバイト列の SHA-256 で比較します。レコードの多いチャンクから順に判断するため、
古くて短いチャンクのコピーは何も追加しません。新しいレコードが一つでもあるチャンクは、まるごと
書き出します。そのチャンクの他のレコードが現行ログにもある場合は、レコードのレポートで示します。

## 出力

```text
carved/
├── Carved/
│   ├── Security.evtx
│   ├── Microsoft-Windows-Sysmon%4Operational.evtx
│   └── ...
├── Recovered/
│   └── Volume1/C/Windows/System32/winevt/Logs/...
├── chunks.csv
└── records.csv
```

**復元したログ。** `Carved/` には、チャネルごとに一つのログを時刻順に書き出します。ファイル名は
Windows のログの名前の付け方に従います（`/` は `%4` になります）。チャネルがわからないチャンクは
`Unknown.evtx` に書き出します。一つのログには最大 65,535 個のチャンクを入れ、それを超える分は
`<name>-2.evtx` などに書き出します。各ログには新しいファイルヘッダーを付けます。各チャンクでは、
ヘッダーのレコード番号を前のチャンクから続くように振り直し、イベント ビューアーで開けるように両方の
チェックサムを計算し直します。割り当て済みのレコードが壊れている場合は、そのレコードと後ろのすべての
レコードをスラックにします。壊れたレコードで読み取りを止めるツールでも、正常なレコードを読める
ようにするためです。それ以外の部分は、スラックも含めてバイト単位でそのまま残します。
Hayabusa の `-x` は空とマークされたチャンクを検索します。使用中のチャンクのスラックに残るレコードは、Juntei の `records.csv` で確認できます。

```bash
hayabusa csv-timeline -d carved/Carved -a -o carved-timeline.csv
```

**チャンクのレポート**（`chunks.csv` / `chunks.jsonl`）には、見つかったチャンクごとに 1 行を書き出します。

| フィールド | 意味 |
|---|---|
| `Source` | 入力ファイルの名前、またはチャンクがあった `Recovered/` 以下の復元したログです。 |
| `Offset` | ソースの中でチャンクが始まる位置です（圧縮されたチャンクでは、その LZNT1 ブロックの位置です）。 |
| `Location`、`Volume`、`Owner` | チャンクがあった場所（上記を参照）、ボリューム番号、チャンクが属するファイルです。 |
| `Status`、`OutputFile` | チャンクの扱い（上記を参照）と、書き出した復元ログです。 |
| `Channel`、`Computer` | レコードで最も多いチャネルとコンピューターです。 |
| `FirstRecordId`、`LastRecordId`、`FirstTime`、`LastTime` | 割り当て済みのレコードの範囲です（UTC）。 |
| `Records`、`SlackRecords`、`DamagedRecords` | 割り当て済みのレコード、スラックにある古いレコード、読めなかった割り当て済みのレコードの数です。 |
| `NewRecords` | 現行ログにないレコードの数です。 |
| `EmptyPage` | 空ページとして書かれていたかどうかです。 |
| `Compressed`、`Truncated` | NTFS 圧縮から展開したかどうか、入力の終わりで途切れたかどうか（残りはゼロです）です。 |
| `HeaderChecksumValid`、`DataChecksumValid` | 保存されていたチェックサムが一致したかどうかです。 |
| `Repaired` | 復元したログで、壊れたレコードとその後ろのレコードをスラックにしたかどうかです。 |

**レコードのレポート**（`records.csv` / `records.jsonl`）には、書き出したチャンクのレコードごとに 1 行を
書き出します。

| フィールド | 意味 |
|---|---|
| `OutputFile`、`Source`、`ChunkOffset`、`Location` | 復元したログと、チャンクが見つかった場所です。 |
| `RecordOffset`、`Allocation` | チャンク内のレコードのオフセットと、`Allocated` または `Slack` です。 |
| `EventRecordId`、`Timestamp` | レコードヘッダーの値です（UTC）。 |
| `Channel`、`EventId`、`Provider`、`Computer` | レコードの値です（スラックのレコードでは空です）。 |
| `OnlyInCarvedData` | 現行ログにないレコードかどうかです。 |

## 制限

- 連続したチャンクだけを見つけられます。空き領域で連続していないクラスターにまたがるチャンクや、
  メモリで連続していない物理ページにまたがるチャンクは不完全です。後ろのレコードが壊れているか
  欠けていることがあり、そのようなチャンクの多くはチェックサムが一致しません。
- `hiberfil.sys` とクラッシュダンプは、先に展開する必要があります。
- スラックのレコードはレコードのレポートに一覧にしますが、チャネルやイベントの詳細はありません。
  イベントログのリーダーでは、チャンクのスラックからレコードを復元する機能がある場合にだけ表示されます。
