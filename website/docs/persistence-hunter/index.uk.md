# Persistence Hunter { #persistence-hunter }

Закріплення (persistence) — це спосіб змусити код запускатися знову: під час запуску Windows, входу користувача, відкриття
програми, настання запланованого часу або іншої події. Зловмисники можуть зловживати тими самими параметрами,
які легітимне програмне забезпечення використовує для оновлень, підтримки пристроїв, безпеки та адміністрування.

`juntei persistence-hunter` офлайн досліджує зібрані докази Windows за допомогою **131 перевірки**, що охоплюють
ці механізми та пов'язані аномалії облікових записів і захисту. Він читає кущі реєстру, файли завдань,
скрипти, параметри програм і вибрані записи баз даних.

На цій сторінці пояснено кожну реалізовану перевірку. Повний перелік параметрів, поля виводу, профілі та
обробку часових позначок наведено в [посібнику з команди](../commands/persistence-hunter.md). У розділі
[Подяки](acknowledgements.md) наведено посилання на проєкт PyrsistenceSniper мовою Python та оригінальний
інструмент PersistenceSniper мовою PowerShell.

## Початок розслідування { #start-an-investigation }

```bash
juntei persistence-hunter -d evidence/ --min-severity info -o PersistenceHunter.csv --coverage Coverage.csv
```

Використовуйте `--min-severity info`, щоб отримати повний перелік кандидатів. Під час ручного запуску команда за замовчуванням використовує
`medium`; її профіль може класифікувати часткові збіги зі списком дозволених як `LOW`, навіть якщо через відсутність доказів щодо корисного навантаження чи
підписувача повне порівняння неможливе. Ні збіг зі списком дозволених, ні незнайомий запис не вирішують питання,
чи є щось шкідливим. `auto-parse` уже зберігає всі рівні серйозності та записує результати
в категорію `persistence/` кожного комп'ютера.

Щоб зосередитися на певному механізмі, скопіюйте його **ідентифікатор перевірки** (Check ID) з наведеного нижче:

```bash
juntei persistence-hunter --list-checks
juntei persistence-hunter -d evidence/ --check run_keys,scheduled_task_files --min-severity info -o focused.csv
```

За замовчуванням команда використовує спільний пул робочих потоків. Додайте `-T 4`, щоб вибрати чотири потоки, або `-T 1`
для однопотокового сканування. Вхідні дані можуть містити кілька комп'ютерів; їхні докази обробляються окремо.

## Читання результатів як доказів { #read-findings-as-evidence }

| Питання | Що перевіряти |
|---|---|
| Що було налаштовано і де? | `CheckId`, `Path` і повне значення `Value`, включно з аргументами. Перейдіть за `SourceFile` до зібраного кущу реєстру, файлу чи бази даних. |
| Чи є ціль у зібраних даних? | `ResolvedPath`, `ResolutionStatus` і `Exists`. Незібрані, неоднозначні або непідтримувані посилання вважаються невідомими; Juntei не підставляє файл з комп'ютера аналітика. |
| Чи діє ця конфігурація? | Фактичний тригер, прапорці ввімкнення, вибраний набір керування, версія Windows/програми, користувач і архітектура. Деякі перевірки навмисно зберігають неактивну конфігурацію. |
| Чи це атака? | `Severity` і `PolicyReason` пояснюють збіг із профілем, а не є вердиктом. Порівнюйте з очікуваним програмним забезпеченням, повною командою, хешами файлів, незалежними доказами виконання та навколишньою часовою шкалою. |
| Хто міг це запустити? | `AccessGained` — підказка щодо області дії/контексту. Для конфігурації рівня всього комп'ютера часто вказано `SYSTEM`, але це не доводить, що запущений процес працював від імені SYSTEM. Принципали завдань і SID власників BITS надають конкретніший контекст, якщо вони доступні. |
| Коли це змінилося? | `KeyLastWrite` датує весь ключ реєстру. `LastChange`, `ChangeSource` і `ChangeEvidence` описують окреме зіставлення з MFT/EVTX, якщо воно доступне. Жодне з цих полів автоматично не датує виконання корисного навантаження. |
| Наскільки надійний відновлений стан? | Читайте `RecordStatus`, `Coverage.csv` і попередження щодо відтворених, вирізаних (carved), пошкоджених, відсутніх або обмежених доказів. Відновлений історичний запис може вже не бути активним. |
| Чи можна довіряти названому видавцю? | `Signer` і `SignerStatus` — це описові метадані PE/сертифіката/каталогу. Juntei не перевіряє підписи Authenticode чи довіру до сертифікатів. |

Відсутність результатів не доводить відсутності закріплення. Рядок охоплення зі значенням `complete` означає,
що відповідне зібране джерело було прочитано, а не те, що зібрані дані містять кожен відповідний файл,
кожного користувача чи кожен можливий механізм закріплення Windows. Інші стани охоплення пояснюють відсутні,
часткові, вимкнені або невдалі перевірки. Цей інструмент не сканує живу пам'ять, мережу чи хмарні ідентичності.

## Каталог і позначення розташувань { #catalogue-and-location-notation }

Каталог ґрунтується на PyrsistenceSniper, а також на власній перевірці `start_menu_com`;
наведені нижче описи документують
власну поведінку Juntei, включно з обмеженнями щодо доказів. Існує **116 перевірок на основі
реєстру і 15 перевірок файлів/репозиторіїв**. Деякі перевірки файлів також об'єднують дані реєстру, тому це
кількості за реалізацією, а не взаємовиключні вимоги до збирання даних. Нижче механізми
згруповано за метою розслідування, а в межах кожної групи впорядковано за абеткою за ідентифікатором перевірки.

- `HKLM\SYSTEM`, `HKLM\SOFTWARE` і `HKLM\SAM` позначають зібрані кущі реєстру комп'ютера, зазвичай
  отримані з `Windows\System32\config`, разом із журналами транзакцій, якщо вони доступні.
- `HKU\<user>` означає відповідний зібраний кущ реєстру користувача. Більшість параметрів користувача походять з NTUSER.DAT;
  реєстрації класів можуть походити з `AppData\Local\Microsoft\Windows\UsrClass.dat`, як зазначено.
- `<ControlSet>` означає вибраний активний набір керування в SYSTEM. Додаткові
  історичні розташування для перевірки DSRM явно вказано нижче. Під час їх перегляду перевіряйте `SYSTEM\Select`.
- `<name>` — змінна складова шляху. У таблицях цілей реєстру `<child>` означає безпосередні
  дочірні реєстрації; це не означає необмеженого рекурсивного обходу. Для перевірок з явною рекурсією
  їхній обхід описано окремо. Квадратні дужки в шляхах Office позначають необов'язкову версію.
- У таблицях наведено фактичні подання реєстру комп'ютера та користувача, які вибирає перевірка. 32-бітне подання вказано там,
  де його реалізовано; не вважайте, що кожна перевірка досліджує всі можливі архітектури/подання.
- Загальні перевірки значень видають непорожні налаштовані записи, включно з елементами багаторядкових значень і
  числовим нулем, де це застосовно. Самі по собі вони не вимагають шкідливого корисного навантаження,
  увімкненого тригера чи успішного виконання. Вибірковіші умови вказано для кожної перевірки окремо.

Ідентифікатори ATT&CK — це успадковані відповідності з каталогу та посилання для подальшого вивчення. Вони описують потенційне
зловживання, а не висновок про те, що зловмисник застосував цю техніку; перевірки параметрів захисту та діагностичні
перевірки можуть описувати умови, що уможливлюють атаку, а не самостійний механізм закріплення.

## Завантаження, вхід і автозапуск { #boot-sign-in-and-startup }

Ці параметри забезпечують запуск команди або бібліотеки під час завантаження, входу в систему чи ініціалізації робочого стола. Перевіряйте версію Windows і відповідного користувача: параметр може бути застарілим, вимкненим або призначеним для кіоску, а не зловмисником.

### Active Setup {#active_setup}

**Ідентифікатор перевірки:** `active_setup` · **ATT&CK за каталогом:** [T1547.014](https://attack.mitre.org/techniques/T1547/014/)

**Що перевіряє Juntei:** читає `StubPath` з реєстрацій компонентів Active Setup рівня всього комп'ютера в нативному та 32-бітному поданнях. Windows може використовувати ці команди під час підготовки профілю користувача; перевірка пропускає буквальні значення-заповнювачі `U` і `/UserInstall`.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\Active Setup\Installed Components\<component>\StubPath` і відповідне дерево `Wow6432Node`.

**Як розслідувати:** порівняйте кожен компонент із відповідним встановленим продуктом і перевірте аргументи команди. Реєстрація рівня всього комп'ютера може призвести до виконання в сеансі користувача, який входить у систему; мітка `SYSTEM` у виводі описує область дії конфігурації, а не доводить токен процесу, що буде запущено.

### Boot Execute {#boot_execute}

**Ідентифікатор перевірки:** `boot_execute` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

**Що перевіряє Juntei:** читає багаторядкове значення `BootExecute` диспетчера сеансів (Session Manager), зберігаючи окремі непорожні записи. Фіксує команди, налаштовані для ранньої фази завантаження.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Session Manager` | `BootExecute` |

**Як розслідувати:** `autocheck autochk *` — звичне значення за замовчуванням, а дискові утиліти можуть додавати легітимні записи. Досліджуйте додані команди та їхні файли, не вважаючи, що кожен нестандартний запис виконувався або є шкідливим.

### Програма перевірки завантаження (Boot Verification Program) {#boot_verification_program}

**Ідентифікатор перевірки:** `boot_verification_program` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

**Що перевіряє Juntei:** читає `ImagePath` з `BootVerificationProgram` — розташування виконуваного файлу, пов'язаного з перевіркою завантаження.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\BootVerificationProgram` | `ImagePath` |

**Як розслідувати:** перевірте, чи застосовний цей старіший механізм до зібраної версії Windows і конфігурації завантаження. Визначте цільовий файл і порівняйте його призначення з очікуваним програмним забезпеченням для керування завантаженням.

### Значення Load у Explorer {#explorer_load}

**Ідентифікатор перевірки:** `explorer_load` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

**Що перевіряє Juntei:** читає значення `Load`, пов'язане з конфігурацією ініціалізації входу в Windows, з кущів реєстру комп'ютера та користувача.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows` | `Load` |
| `HKU\<user>\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Windows` | `Load` |

**Як розслідувати:** досліджуйте незнайомі команди, призначення з правом запису для користувача та аргументи, які завантажують або декодують вміст. Окремо підтверджуйте застосовність і виконання; порожній результат не охоплює інших механізмів входу.

### Драйвери шрифтів {#font_drivers}

**Ідентифікатор перевірки:** `font_drivers` · **ATT&CK за каталогом:** [T1547](https://attack.mitre.org/techniques/T1547/)

**Що перевіряє Juntei:** перелічує непорожні значення в застарілому ключі реєстру `Font Drivers` як потенційні реєстрації бібліотек.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Font Drivers` | Усі непорожні значення |

**Як розслідувати:** розглядайте це як незвичну застарілу поверхню конфігурації. Перш ніж робити висновок про можливість завантаження, перевірте підтримку у відповідній версії Windows і саму бібліотеку, а фактичне використання підтверджуйте доказами процесів або завантаження образів.

### DLL розширень групової політики {#gp_extension_dlls}

**Ідентифікатор перевірки:** `gp_extension_dlls` · **ATT&CK за каталогом:** [T1574.001](https://attack.mitre.org/techniques/T1574/001/)

**Що перевіряє Juntei:** читає `DllName` з кожної безпосередньої реєстрації розширення групової політики в Winlogon. Ці DLL розширюють обробку політик.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\GPExtensions\<child>` | `DllName` |

**Як розслідувати:** розширення можуть установлювати продукти для керування та захисту. Зіставте GUID розширення та DLL з очікуваним продуктом і, перш ніж стверджувати про виконання, вивчіть докази обробки політик і завантаження образів.

### Скрипти групової політики {#gp_scripts}

**Ідентифікатор перевірки:** `gp_scripts` · **ATT&CK за каталогом:** [T1037.001](https://attack.mitre.org/techniques/T1037/001/)

**Що перевіряє Juntei:** розбирає пари команда/параметри із зібраних файлів реєстрації локальної групової політики `scripts.ini` і `psscripts.ini`, включно з локальними сховищами політик окремих користувачів. Розділи запуску/завершення роботи та входу/виходу зберігають налаштовані команди й аргументи, причому розділи комп'ютера відрізняються від розділів користувача.

**Досліджувані докази:**

- `Windows\System32\GroupPolicy\Machine\Scripts\scripts.ini` / `psscripts.ini` та відповідні файли `GroupPolicy\User\Scripts`.
- `Windows\System32\GroupPolicyUsers\<SID>\User\Scripts\scripts.ini` / `psscripts.ini`.

**Як розслідувати:** досліджуються лише реалізовані розташування реєстрації локальних політик; це не повний аудит SYSVOL/GPO. Файлу скрипту, що лежить деінде в каталозі політик, недостатньо. Зіставляйте його реєстрацію з доказами обробки політик і виконання.

### Скрипти входу (UserInitMprLogonScript) {#logon_scripts}

**Ідентифікатор перевірки:** `logon_scripts` · **ATT&CK за каталогом:** [T1037.001](https://attack.mitre.org/techniques/T1037/001/)

**Що перевіряє Juntei:** читає значення середовища користувача `UserInitMprLogonScript`, яке може вибирати скрипт для входу цього користувача.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKU\<user>\Environment` | `UserInitMprLogonScript` |

**Як розслідувати:** порівняйте із затвердженими скриптами входу та перевірте сам скрипт. Значення не доводить подальшого входу чи виконання, а для скриптів, що надаються доменом, потрібні додаткові докази щодо політик.

### Platform Execute {#platform_execute}

**Ідентифікатор перевірки:** `platform_execute` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

**Що перевіряє Juntei:** читає кожен непорожній запис `PlatformExecute` у Session Manager. Визначає програми, вибрані для пов'язаної з платформою ініціалізації під час завантаження.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|

## Заплановані завдання { #scheduled-tasks }

Планувальник завдань зберігає конфігурацію як у файлах XML, так і в кущі реєстру SOFTWARE. Читайте ці джерела разом. Завдання може бути зареєстроване, але жодного разу не запускатися, а неповне збирання даних може нагадувати приховане завдання чи завдання-привид.

### Заплановане завдання-привид {#ghost_task}

**Ідентифікатор перевірки:** `ghost_task` · **ATT&CK за каталогом:** [T1053.005](https://attack.mitre.org/techniques/T1053/005/)

**Що перевіряє Juntei:** порівнює реєстрації `Tree` і `Tasks` у TaskCache куща SOFTWARE і, якщо файли завдань є серед зібраних даних, шукає відповідні XML-файли завдань.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree` і `TaskCache\Tasks`.
- Зібрані файли `Windows\System32\Tasks\<task path>` для порівняння з файловою системою.

**Як розслідувати:** відсутність відповідників може свідчити про видалені/застарілі завдання, вбудовані реєстрації або неповне збирання даних. Якщо XML не зібрано, порівняння з файловою системою недоступне. Перш ніж називати завдання прихованим чи шкідливим, перевірте охоплення та точну розбіжність.

### Приховане заплановане завдання {#hidden_scheduled_task}

**Ідентифікатор перевірки:** `hidden_scheduled_task` · **ATT&CK за каталогом:** [T1053.005](https://attack.mitre.org/techniques/T1053/005/)

**Що перевіряє Juntei:** перевіряє реєстрації Tree у TaskCache на відсутність значення `SD` або порожній двійковий дескриптор безпеки — умови, пов'язані з приховуванням завдання від звичайного переліку.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tree\<task>`: наявність/дані `SD` разом із метаданими відповідника в TaskCache.

**Як розслідувати:** відсутній/порожній SD — це конкретна аномалія конфігурації, а не доказ того, що завдання виконувалося чи є шкідливим. Параметр XML `Hidden` і довільні проблеми з ACL — це інші умови, і вони не є критерієм, який тут використовується.

**Додаткові відомості:** [документація Microsoft](https://www.microsoft.com/en-us/security/blog/2022/04/12/tarrask-malware-uses-scheduled-task-defense-evasion/).

### Заплановане завдання (файли XML) {#scheduled_task_files}

**Ідентифікатор перевірки:** `scheduled_task_files` · **ATT&CK за каталогом:** [T1053.005](https://attack.mitre.org/techniques/T1053/005/)

**Що перевіряє Juntei:** розбирає зібрані XML-файли завдань, отримуючи команди/аргументи Exec, а також ідентифікатори класів і дані COM-обробників. Вибирає принципала за `Actions Context`/`Principal id`, окремо зберігає ідентичність користувача і групи та повідомляє SYSTEM, USER або UNKNOWN. Невизначені COM-дії залишаються видимими.

**Досліджувані докази:**

- XML-файли `Windows\System32\Tasks\<task path>`, включно з Exec, ComHandler і доступними полями принципала.
- Зібраний `UsrClass.dat` і `Software\Classes` у NTUSER відповідного користувача, а також `Classes\CLSID` у SOFTWARE комп'ютера в нативному та 32-бітному поданнях.
- Зібраний `ProfileList` у SOFTWARE для принципалів, заданих SID. Для іменованих принципалів перевага надається унікальній відповідній папці `user.DOMAIN`, потім суфіксам зібраного локального хоста і, зрештою, простій папці `user`. Збіги явно позначаються як евристичні; справжня неоднозначність залишається невизначеною і зазначається в результаті та охопленні. Енергозалежні ключі реєстру не потрібні.
- Керований `CodeBase` (включно з підрозділами версій), асоціації AppID і `ImagePath` служби в SYSTEM для `LocalService` в AppID.

Кандидати COM-серверів містять джерело в реєстрі в полі `Description`. Асоціації AppID,
що містять лише ім'я виконуваного файлу, залишаються невизначеними, а не отримують вгаданий каталог. Локальні
URL-адреси `file:` декодуються; віддалені URL-адреси зберігаються без звернення до мережі. Перевизначення класів користувача
обмежені відповідним профілем, а неповний CLSID користувача не переходить до затіненої ним
реєстрації комп'ютера. Завдання лише з групою зберігають кандидатів комп'ютера з приміткою про обмеження щодо окремих
користувачів в описі, не додаючи рутинних повідомлень до зведення помилок охоплення.

**Як розслідувати:** перевірте тригери, стан увімкнення, принципала та історію запусків у вихідному XML і журналах подій. Створене завдання може жодного разу не запуститися. Невизначений COM-обробник усе одно є кандидатом, а відсутність даних принципала або наявність лише групи не можна вважати ознакою SYSTEM.

## WMI, BITS та інші тригери подій { #wmi-bits-and-other-event-triggers }

Windows Management Instrumentation (WMI) підтримує керування системою. Background Intelligent Transfer Service (BITS) підтримує фонові передавання даних. Обидва механізми можуть зберігати команди, що запускаються подіями. Деякі механізми очікують на подію керування, сповіщення про передавання, запуск програми чи дію користувача. Збережений тригер — корисний доказ конфігурації, але його наявність не встановлює, що тригер спрацював.

### Бекдор через спеціальні можливості {#accessibility_tools}

**Ідентифікатор перевірки:** `accessibility_tools` · **ATT&CK за каталогом:** [T1546.008](https://attack.mitre.org/techniques/T1546/008/)

**Що перевіряє Juntei:** порівнює сім зібраних двійкових файлів спеціальних можливостей із System32 за PE OriginalFilename і метаданими сертифіката/каталогу, попередньо вимагаючи придатні до використання метадані каталогу Microsoft від зібраного еталонного двійкового файлу.

**Досліджувані докази:**

- `Windows\System32\sethc.exe`, `osk.exe`, `narrator.exe`, `magnify.exe`, `utilman.exe`, `atbroker.exe` і `DisplaySwitch.exe`.
- Еталонні метадані зібраних `Windows\System32\winlogon.exe`, `cmd.exe` або `notepad.exe` і застосовні зібрані каталоги.

**Як розслідувати:** метадані можуть вказувати на перейменований замінник, але Juntei не перевіряє підписи чи довіру до сертифікатів. Розріджене збирання без потрібних каталогів дає неповне охоплення порівняння, а не призводить до того, що кожен файл, який виглядає непідписаним, вважається бекдором.

### Спеціальні можливості {#assistive_technology}

**Ідентифікатор перевірки:** `assistive_technology` · **ATT&CK за каталогом:** [T1546.008](https://attack.mitre.org/techniques/T1546/008/)

**Що перевіряє Juntei:** читає зареєстровані команди спеціальних можливостей `StartExe` разом зі `StartParams` у нативному/32-бітному поданнях SOFTWARE, а також увімкнені записи `Configuration` спеціальних можливостей із кущів користувачів і DEFAULT. Числові/нерядкові заповнювачі StartExe пропускаються.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Accessibility\ATs\<feature>`: `StartExe` і `StartParams`; також подання `Wow6432Node` комп'ютера.
- `HKU\<user>\Software\Microsoft\Windows NT\CurrentVersion\Accessibility\Configuration` у NTUSER.DAT і відповідний параметр у кущі DEFAULT.

**Як розслідувати:** програмне забезпечення спеціальних можливостей є легітимним. Розрізняйте назву увімкненої функції та фактичну реєстрацію її виконуваного файлу, а потім перевірте ціль і докази виконання під час входу/на робочому столі. Це окрема ситуація від заміни самого виконуваного файлу спеціальних можливостей.

**Додаткові відомості:** [опис техніки (hexacorn.com)](https://www.hexacorn.com/blog/2016/07/22/beyond-good-ol-run-key-part-42/).

### Команда сповіщення завдання BITS {#bits_notify_command}

Час запису бази даних у MFT — слабкий доказ щодо контейнера, а не час виконання сповіщення. SID власників дають змогу розрізнити SYSTEM, локальну службу, мережеву службу та користувачів.

## Провідник, COM та обробники файлів або URL { #explorer-com-and-file-or-url-handlers }

Component Object Model (COM) дає змогу програмам активувати зареєстровані програмні компоненти. Оболонка Windows використовує зареєстровані обробники для відкриття файлів, URL-адрес, папок і спеціальних об'єктів. Ідентифікатори COM (CLSID) визначають компоненти; ProgID надають деяким компонентам зрозумілі назви. Простежуйте кожну реєстрацію до команди або DLL, яку вона вибирає.

### Перехоплення App Paths {#app_paths}

**Ідентифікатор перевірки:** `app_paths` · **ATT&CK за каталогом:** [T1546](https://attack.mitre.org/techniques/T1546/)

**Що перевіряє Juntei:** читає значення за замовчуванням у реєстраціях `App Paths` рівня всього комп'ютера, які можуть перенаправляти пошук програм під час запуску через оболонку.

**Досліджувані докази:**

- Значення за замовчуванням `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\<application>`.

**Як розслідувати:** реєстрація App Paths поширена серед встановлених програм і не є загальним перевизначенням кожного запуску процесу. Порівняйте зареєстроване ім'я та образ з очікуваним програмним забезпеченням, а потім вивчіть відповідні докази оболонки/процесів.

### Перехоплення COM-об'єкта {#com_treat_as}

**Ідентифікатор перевірки:** `com_treat_as` · **ATT&CK за каталогом:** [T1546.015](https://attack.mitre.org/techniques/T1546/015/)

**Що перевіряє Juntei:** знаходить перенаправлення COM `TreatAs` і реєстрації InprocServer32/LocalServer32 окремих користувачів, що затінюють CLSID комп'ютера, у підтримуваних нативних/32-бітних сховищах класів. Цілі TreatAs визначаються з використанням класів того самого користувача та класів комп'ютера.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Classes\CLSID\<CLSID>` і подання `Classes\Wow6432Node` комп'ютера.
- `Software\Classes\CLSID` користувача в NTUSER.DAT і `CLSID` в UsrClass.dat, включно з реалізованими поданнями `Wow6432Node`: значення за замовчуванням `TreatAs`, `InprocServer32` і `LocalServer32`.

**Як розслідувати:** перевизначення на рівні користувача можуть не потребувати прав адміністратора, але їх також може реєструвати легітимне програмне забезпечення. Простежте вибраний клас і DLL/виконуваний файл, оцініть архітектуру й контекст активації та незалежно підтвердьте фактичну активацію COM.

### Перехоплення обробника очищення диска {#disk_cleanup_handler}

**Ідентифікатор перевірки:** `disk_cleanup_handler` · **ATT&CK за каталогом:** [T1546.015](https://attack.mitre.org/techniques/T1546/015/)

**Що перевіряє Juntei:** читає CLSID обробників VolumeCaches засобу очищення диска і простежує придатні до визначення реєстрації COM InprocServer32 комп'ютера до їхніх бібліотек.

**Досліджувані докази:**

- CLSID за замовчуванням у `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\VolumeCaches\<handler>` і `Classes\CLSID\<CLSID>\InprocServer32`.

**Як розслідувати:** для запуску обробник має бути викликаний відповідним процесом очищення. Ця перевірка не видає невизначених обробників, тому, якщо зібрані дані неповні, перевіряйте їхні необроблені реєстрації за допомогою парсера реєстру.

### Перевизначення AppKey у Explorer {#explorer_app_key}

**Ідентифікатор перевірки:** `explorer_app_key` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

**Як розслідувати:** ці значення можуть задавати утиліти клавіатури та інструменти OEM. Назва асоціації може вимагати ще одного переходу в реєстрі, а не бути шляхом до файлу. Перевірте дію користувача, яка її запускала б.

### Об'єкти допомоги браузеру (BHO) {#explorer_bho}

**Ідентифікатор перевірки:** `explorer_bho` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

### Закріплення через COM у бібліотеках меню «Пуск» і папках з CLSID {#start_menu_com}

**Ідентифікатор перевірки:** `start_menu_com` · **ATT&CK за каталогом:** [T1546.015](https://attack.mitre.org/techniques/T1546/015/)

**Що перевіряє Juntei:** знаходить XML-файли бібліотек `.library-ms`, URL-адреса `simpleLocation` яких посилається
на CLSID COM, а також каталоги з іменами `<name>.{CLSID}` у
`Users\<user>\AppData\Roaming\Microsoft\Windows\Start Menu`. Взаємодія Explorer з цими
об'єктами може активувати код COM. Перевірка охоплює порожні зібрані каталоги; вона не переходить за
символічними посиланнями. Звичайні файли бібліотек поза меню «Пуск» і GUID у коментарях XML
ця перевірка не повідомляє.

**Досліджувані докази:**

- Файли `.library-ms` і записи каталогів з іменами-CLSID у меню «Пуск» кожного користувача.
- Зібрані реєстрації класів відповідного користувача та SOFTWARE комп'ютера, окремо для кожної архітектури.
- Конфігурація керованого CodeBase/AppID/служби за допомогою того самого механізму визначення, що й для запланованих завдань.

**Як розслідувати:** `Path` і `SourceFile` визначають артефакт, що слугує тригером активації. `Value`
містить команду сервера-кандидата або CLSID, якщо визначення недоступне. `Description`
пов'язує тригер із CLSID і зібраним джерелом у реєстрі. `ResolvedPath`/`Sha256` описують лише
визначене та зібране корисне навантаження. Асоціація AppID, що містить лише ім'я виконуваного файлу, залишається невизначеною.
Тригер може бути легітимним; його наявність не доводить входу, активації, виконання чи атаки.
Перевірте URL-адресу бібліотеки, реєстрацію класу, корисне навантаження, контекст користувача та незалежні журнали виконання.

**Застереження щодо збирання:** під час збирання лише файлів порожні каталоги можуть бути пропущені. Досліджуються стандартні шляхи
меню «Пуск» користувачів; перенаправлені меню «Пуск» та інші розташування простору імен Explorer ця перевірка
не охоплює. Відсутні кущі реєстру або невизначені реєстрації дають часткове охоплення, проте кандидат
зберігається. Архітектура завдання, підвищення привілеїв і політика можуть змінювати фактичну поведінку пошуку COM.

**Додаткові відомості:** [початкова пропозиція та подяка досліднику](https://github.com/last-byte/PersistenceSniper/pull/32),
[об'єднані подання COM для користувача/комп'ютера](https://learn.microsoft.com/en-us/windows/win32/sysinfo/merged-view-of-hkey-classes-root),
[MITRE: перехоплення COM](https://attack.mitre.org/techniques/T1546/015/).

### Перехоплення COM через TypeLib {#typelib_hijack}

## Програми Office і надбудови { #office-applications-and-add-ins }

Office підтримує легітимні надбудови, шаблони та розширення для окремих програм. Підозріла реєстрація може залежати від конкретної версії Office, програми, параметра завантаження або взаємодії користувача. Сама конфігурація не встановлює виконання макросів.

### Реєстрація надбудов Office {#office_addins}

**Ідентифікатор перевірки:** `office_addins` · **ATT&CK за каталогом:** [T1137.006](https://attack.mitre.org/techniques/T1137/006/)

**Що перевіряє Juntei:** перелічує надбудови Word, Excel, PowerPoint, Outlook і Access у кореневих розділах Office без версії та з версіями 14.0/15.0/16.0, включно з реалізованим сховищем Click-to-Run комп'ютера та кореневими розділами користувачів. Зберігає явні значення Manifest/FileName/Path або визначає відповідні записи на основі COM разом із контекстом LoadBehavior.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\Office\[<version>\]<application>\Addins\<add-in>` і реалізований відповідник Click-to-Run комп'ютера.
- `HKU\<user>\Software\Microsoft\Office\[<version>\]<application>\Addins\<add-in>` у NTUSER.DAT; відповідні класи COM комп'ютера/користувача з SOFTWARE, NTUSER.DAT і UsrClass.dat.

**Як розслідувати:** надбудови — поширене бізнесове програмне забезпечення. Перегляньте LoadBehavior, програму/версію, маніфести, фактичні корисні навантаження та очікуваного постачальника. Перевірка не гарантує, що кожен формат встановлених надбудов або подання реєстрації було зібрано чи завантажено.

### Перехоплення AI-надбудови Office {#office_ai_hijack}

**Як розслідувати:** порівняйте незвичайні значення та шляхи зі встановленою збіркою Office. Наявність значення не показує, яка функція Office його використовувала, і не доводить, що воно вибирало виконуваний код.

### Шаблони Office за замовчуванням {#office_templates}

## Параметри середовища виконання .NET і профілювальників { #net-runtime-and-profiler-settings }

Керовані середовища виконання можуть завантажувати профілювальники, стартові збірки або бібліотеки налагодження раніше за код програми. Ці параметри також використовують розробники та продукти моніторингу. Перевіряйте середовище виконання, архітектуру процесу, прапорці ввімкнення і те, чи міг новозапущений процес успадкувати параметр.

### Ін'єкція через AppDomainManager {#appdomain_manager}

**Ідентифікатор перевірки:** `appdomain_manager` · **ATT&CK за каталогом:** [T1574.014](https://attack.mitre.org/techniques/T1574/014/)

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Session Manager\Environment` | `APPDOMAIN_MANAGER_ASM` |
| `HKLM\SYSTEM\<ControlSet>\Control\Session Manager\Environment` | `APPDOMAIN_MANAGER_TYPE` |
| `HKU\<user>\Environment` | `APPDOMAIN_MANAGER_ASM` |
| `HKU\<user>\Environment` | `APPDOMAIN_MANAGER_TYPE` |

**Як розслідувати:** програми можуть навмисно використовувати користувацькі диспетчери. Визначайте збірку та тип разом і перевіряйте сумісність середовища виконання та успадкування процесами; ні окрема змінна, ні часова позначка її ключа не доводять, що керована програма її завантажувала.

### Перехоплення профілювальника .NET CLR {#cor_profiler}

**Ідентифікатор перевірки:** `cor_profiler` · **ATT&CK за каталогом:** [T1574.012](https://attack.mitre.org/techniques/T1574/012/)

**Що перевіряє Juntei:** читає параметри середовища профілювання COR комп'ютера/користувача та відповідні іменовані записи в багаторядкових значеннях Environment окремих служб. Зберігає прапорці ввімкнення, ідентифікатори профілювальників і шляхи для конкретних архітектур.

**Досліджувані докази:**

- `HKLM\SYSTEM\<ControlSet>\Control\Session Manager\Environment` і `Environment` у кожному зібраному NTUSER.DAT користувача.
- `HKLM\SYSTEM\<ControlSet>\Services\<service>\Environment`: іменовані параметри COR у багаторядковому значенні.

**Як розслідувати:** профілювальники підтримують легітимний моніторинг. Прапорець ввімкнення, CLSID і шлях до DLL — різні частини конфігурації; підтвердьте фактичне ввімкнення та відповідний процес .NET, а не вважайте кожен рядок виконаним профілювальником.

## Перевизначення пошуку DLL і виконуваних файлів { #dll-and-executable-lookup-overrides }

Ці перевірки досліджують явні розташування бібліотек або параметри, що впливають на те, як компонент знаходить код. Перевизначення шляху або послаблена політика пошуку — це зачіпка для розслідування; для виконання все одно потрібні корисне навантаження та сумісний компонент-тригер.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\NlsData` | `DllOverridePath` |

**Як розслідувати:** перегляньте цільову бібліотеку, збірку Windows і компонент обробки природної мови, який міг би використовувати перевизначення. Значення не свідчить про те, що відбувалося індексування чи мовна обробка.

### DLL RDP TestDVCPlugin {#rdp_test_dvc_plugin}

**Ідентифікатор перевірки:** `rdp_test_dvc_plugin` · **ATT&CK за каталогом:** [T1574.001](https://attack.mitre.org/techniques/T1574/001/)

**Що перевіряє Juntei:** читає параметр бібліотеки `TestDVCPlugin` клієнта Terminal Server комп'ютера.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Terminal Server Client` | `TestDVCPlugin` |

**Як розслідувати:** дослідіть незнайомий тестовий плагін і поведінку, специфічну для версії. Для встановлення виконання потрібні сумісний клієнтський сеанс і завантаження бібліотеки; саме значення реєстру не свідчить ні про те, ні про інше.

### Перевизначення DLL індексатора пошуку {#search_indexer_dll}

**Ідентифікатор перевірки:** `search_indexer_dll` · **ATT&CK за каталогом:** [T1574.001](https://attack.mitre.org/techniques/T1574/001/)

**Що перевіряє Juntei:** читає перевизначення `DllPath` служби Windows Search із SOFTWARE.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SOFTWARE\Microsoft\Windows Search` | `DllPath` |

**Як розслідувати:** визначте відповідний компонент/версію Search і перевірте цільовий файл. Неактивна служба Windows Search або невикористаний параметр — це не те саме, що спостережене завантаження шкідливої бібліотеки.

### DLL Winsock AutoProxy {#winsock_auto_proxy}

**Ідентифікатор перевірки:** `winsock_auto_proxy` · **ATT&CK за каталогом:** [T1574.001](https://attack.mitre.org/techniques/T1574/001/)

**Що перевіряє Juntei:** читає `LibraryPath` у безпосередніх реєстраціях Catalog_Entries і Catalog_Entries64 у NameSpace_Catalog5.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Services\WinSock2\Parameters\NameSpace_Catalog5\Catalog_Entries\<child>` | `LibraryPath` |
| `HKLM\SYSTEM\<ControlSet>\Services\WinSock2\Parameters\NameSpace_Catalog5\Catalog_Entries64\<child>` | `LibraryPath` |

**Як розслідувати:** мережеві постачальники можуть бути легітимними. Перегляньте обидві архітектури, походження постачальника та відповідні докази мережевих програм/завантаження образів. Цей цільовий пошук постачальників простору імен охоплює не всі можливі розширення Winsock.

## Облікові записи та видимість під час входу { #accounts-and-sign-in-visibility }

Записи локальних облікових записів і параметри видимості під час входу можуть виявити закріплення на основі ідентичності. Ці перевірки досліджують зібрані кущі реєстру SAM і SOFTWARE; вони не є інвентаризацією облікових записів Active Directory, членства в доменних групах чи минулих входів.

### Членство в групі Administrators {#admin_group_membership}

**Ідентифікатор перевірки:** `admin_group_membership` · **ATT&CK за каталогом:** [T1098](https://attack.mitre.org/techniques/T1098/)

**Що перевіряє Juntei:** декодує список членів локального псевдоніма Administrators із SAM. Повідомляє про SID локального комп'ютера, які вказують на прихований обліковий запис або на обліковий запис/групу, відсутні в зібраному SAM.

**Досліджувані докази:**

- `SAM\Domains\Builtin\Aliases\00000220\C` і записи SID комп'ютера/користувачів/груп у `SAM\Domains\Account` у кущі SAM.
- `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\SpecialAccounts\UserList` для зіставлення прихованих імен.

**Як розслідувати:** це цільова перевірка аномалій, а не список усіх адміністраторів. Зовнішні/доменні SID не оцінюються як відсутні локальні користувачі. Видалені облікові записи, момент збирання даних або неповні кущі реєстру потребують дослідження, перш ніж робити висновок про шкідливе членство.

### Прихований локальний обліковий запис {#hidden_account}

**Ідентифікатор перевірки:** `hidden_account` · **ATT&CK за каталогом:** [T1564.002](https://attack.mitre.org/techniques/T1564/002/)

**Що перевіряє Juntei:** повідомляє про числові нульові значення в Winlogon SpecialAccounts UserList, визначаючи імена, приховані від звичайного екрана входу.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon\SpecialAccounts\UserList`: значення з іменами облікових записів.

**Як розслідувати:** облікові записи служб або обслуговування можуть бути приховані навмисно, а значення не встановлює, що названий обліковий запис існує чи є адміністратором. Об'єднуйте із записами облікових записів SAM і активністю входів.

### Перехоплення RID {#rid_hijacking}

**Ідентифікатор перевірки:** `rid_hijacking` · **ATT&CK за каталогом:** [T1098](https://attack.mitre.org/techniques/T1098/)

**Що перевіряє Juntei:** порівнює шістнадцятковий RID підрозділу облікового запису SAM з RID, збереженим за зміщенням 0x30 у його значенні F, і повідомляє про невідповідності.

**Досліджувані докази:**

- `SAM\Domains\Account\Users\<hexadecimal RID>\F` у кущі SAM.

**Як розслідувати:** невідповідність — серйозна аномалія запису облікового запису, але вона також може вимагати аналізу пошкодження/збирання даних. Перевірте вихідні байти, стан журналів транзакцій і записи облікових записів/входів; це не доводить, хто саме змінив запис.

### RID Suborner (прихований обліковий запис адміністратора) {#rid_suborner}

**Ідентифікатор перевірки:** `rid_suborner` · **ATT&CK за каталогом:** [T1098](https://attack.mitre.org/techniques/T1098/)

**Що перевіряє Juntei:** повідомляє про облікові записи SAM, у яких RID підрозділу не дорівнює 500, але RID у значенні F дорівнює 500, — конкретніший шаблон підміни ідентичності адміністратора.

**Досліджувані докази:**

- `SAM\Domains\Account\Users\<hexadecimal RID>\F` у кущі SAM.

**Як розслідувати:** це перетинається із загальною перевіркою невідповідності RID. Попри назву в каталозі, перевірка окремо не вимагає параметра приховування під час входу; видимість облікового запису, привілеї та фактичне використання облікового запису підтверджуйте окремо.

## Компоненти автентифікації та захист облікових даних { #authentication-components-and-credential-protection }

Local Security Authority (LSA) виконує функції безпеки через LSASS і пов'язані компоненти. Пакети автентифікації, фільтри паролів і мережеві постачальники можуть бути легітимним програмним забезпеченням безпеки або шляхом до постійного доступу до облікових даних. Дві перевірки інвентаризують параметри захисту, а не виконувані автозапуски. Інтерпретуйте їх з урахуванням ролі хоста, версії Windows і фактичної політики.

### DLL постачальника AMSI {#amsi_providers}

**Ідентифікатор перевірки:** `amsi_providers` · **ATT&CK за каталогом:** [T1546.015](https://attack.mitre.org/techniques/T1546/015/)

**Що перевіряє Juntei:** перелічує CLSID постачальників AMSI комп'ютера і, якщо можливо, визначає їхні бібліотеки InprocServer32 у нативному/32-бітному поданнях. Невизначені реєстрації зберігають ідентифікатор класу.

**Досліджувані докази:**

- `HKLM\SOFTWARE\Microsoft\AMSI\Providers\<CLSID>` і придатні до визначення реєстрації InprocServer32 у `Classes\CLSID` / `Classes\Wow6432Node\CLSID`.

**Як розслідувати:** антивірусні програми та засоби захисту легітимно реєструють постачальників AMSI. Перегляньте походження постачальника/бібліотеки та фактичне завантаження; реєстрація не доводить, що AMSI було обійдено або що постачальник був шкідливим.

### Пакети автентифікації {#authentication_packages}

**Ідентифікатор перевірки:** `authentication_packages` · **ATT&CK за каталогом:** [T1547.002](https://attack.mitre.org/techniques/T1547/002/)

**Що перевіряє Juntei:** читає окремі непорожні записи LSA `Authentication Packages` з активного набору керування.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Lsa` | `Authentication Packages` |

**Як розслідувати:** порівняйте з вихідною збіркою Windows і встановленим програмним забезпеченням автентифікації. Нестандартний пакет може бути легітимним. Перш ніж робити висновок про перехоплення, визначте DLL і підтвердьте завантаження/активність з обліковими даними.

### Поведінка входу адміністратора DSRM {#dsrm_backdoor}

**Ідентифікатор перевірки:** `dsrm_backdoor` · **ATT&CK за каталогом:** [T1547.001](https://attack.mitre.org/techniques/T1547/001/)

**Що перевіряє Juntei:** повідомляє про числове значення `DsrmAdminLogonBehavior=2` у реалізованих розташуваннях ControlSet001, ControlSet002 або CurrentControlSet. Цей параметр може дозволяти використання облікового запису DSRM поза його звичайним контекстом відновлення.

**Досліджувані докази:**

- `HKLM\SYSTEM\ControlSet001\Control\Lsa\DsrmAdminLogonBehavior`, а також ControlSet002 і CurrentControlSet, якщо вони наявні.

**Як розслідувати:** стосується насамперед контролерів домену. Визначте, який набір керування активний, за допомогою SYSTEM Select; збіг в історичному наборі керування не обов'язково є чинним. Значення не доводить, що зловмисник знав пароль DSRM або входив у систему.

### Конфігурація Credential Guard {#lsa_cfg_flags}

**Ідентифікатор перевірки:** `lsa_cfg_flags` · **ATT&CK за каталогом:** [T1547.008](https://attack.mitre.org/techniques/T1547/008/)

**Що перевіряє Juntei:** читає налаштоване значення LSA `LsaCfgFlags`, включно як зі звичайними значеннями ввімкнення, так і з нулем. Це інвентаризація конфігурації Credential Guard, а не виконуваного автозапуску.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Lsa` | `LsaCfgFlags` |

**Як розслідувати:** інтерпретуйте значення з урахуванням версії Windows, передумов мікропрограми/безпеки та фактичної політики. Збережений нуль або відсутнє значення саме по собі не встановлює зміни, внесеної зловмисником, фактичного стану захисту чи викрадення облікових даних.

### Фільтр паролів LSA {#lsa_password_filter}

**Ідентифікатор перевірки:** `lsa_password_filter` · **ATT&CK за каталогом:** [T1556.002](https://attack.mitre.org/techniques/T1556/002/)

**Що перевіряє Juntei:** читає LSA `Notification Packages`. Голі імена бібліотек визначаються відносно зібраного каталогу Windows System32, із додаванням `.dll`, де це доречно.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Lsa` | `Notification Packages` |

**Як розслідувати:** продукти для політик паролів часто встановлюють фільтри. Перевірте бібліотеку та докази завантаження і відрізняйте налаштовані фільтри від доказу того, що відбулася зміна пароля чи перехоплення облікових даних.

### Стан захисту LSASS PPL {#lsa_run_as_ppl}

**Ідентифікатор перевірки:** `lsa_run_as_ppl` · **ATT&CK за каталогом:** [T1547.008](https://attack.mitre.org/techniques/T1547/008/)

**Що перевіряє Juntei:** читає налаштоване значення LSA `RunAsPPL`, включно з ненульовими значеннями. Це інвентаризація параметра захисту, а не перевірка того, що LSASS працював без захисту.

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Lsa` | `RunAsPPL` |

**Як розслідувати:** фактичний захист LSA залежить від версії Windows, політики, блокування мікропрограмою та стану перезапуску. Відсутність рядка для відсутнього значення не є виміряним результатом захисту. Для оцінювання фактичного захисту використовуйте незалежні докази системи/середовища виконання.

### DLL мережевого постачальника {#network_provider_dll}

**Ідентифікатор перевірки:** `network_provider_dll` · **ATT&CK за каталогом:** [T1556.008](https://attack.mitre.org/techniques/T1556/008/)

**Що перевіряє Juntei:** читає `NetworkProvider\ProviderPath` у службах активного набору керування SYSTEM.

**Досліджувані докази:**

- `HKLM\SYSTEM\<ControlSet>\Services\<service>\NetworkProvider\ProviderPath`.

**Як розслідувати:** постачальники мережевого входу можуть бути легітимними. Перевірте порядок/застосовність постачальників, встановлене мережеве програмне забезпечення та засоби захисту, а також фактичне завантаження бібліотеки; саме значення ProviderPath не доводить перехоплення облікових даних.

### Пакети безпеки {#security_packages}

**Ідентифікатор перевірки:** `security_packages` · **ATT&CK за каталогом:** [T1547.005](https://attack.mitre.org/techniques/T1547/005/)

**Що перевіряє Juntei:** читає окремі непорожні записи LSA `Security Packages`, що охоплюють налаштованих постачальників підтримки безпеки (SSP).

**Досліджувані докази:**

| Ключ реєстру | Досліджуване значення |
|---|---|
| `HKLM\SYSTEM\<ControlSet>\Control\Lsa` | `Security Packages` |

**Як розслідувати:** порівняйте з очікуваною базовою конфігурацією Windows/засобів захисту та перевірте кожну бібліотеку. Конфігурація не доводить, що постачальник завантажувався, перехоплював облікові дані чи був доданий під час інциденту.

## Від кандидата до висновку { #work-from-a-candidate-to-a-conclusion }

1. Відкрийте вихідне джерело, визначене в `SourceFile`. Підтвердьте повне значення, дію в XML,
   скрипт або відновлений запис бази даних, а також точного користувача/хост, до якого він належить.
2. Визначте, чи міг механізм працювати: перевірте прапорці ввімкнення, версію середовища виконання або Windows,
   стан служби/завдання, потрібний тригер, користувача, архітектуру та активний набір керування.
3. Перевірте вибрану програму, DLL, скрипт або збірку. Обчисліть хеші зібраних байтів і перегляньте аргументи
   та вміст. Впізнаваний засіб запуску Windows або рядок видавця не вирішують питання легітимності.
4. Встановіть, що фактично відбулося, за допомогою незалежних доказів. Приклади: створення процесів,
   завантаження образів у Sysmon, записи про виконання Task Scheduler, активність служб, Prefetch і пов'язані файли.
   Подія зміни конфігурації може довести, що параметр змінився, але не доводить, що його корисне навантаження виконувалося.
5. Побудуйте часову шкалу, використовуючи часові позначки вихідних джерел і зафіксоване походження зіставлень.
   Записи ключів, зміни установлення, записи файлів/контейнерів і виконання розглядайте як окремі факти.
6. Фіксуйте не лише результати, а й обмеження: відсутні кущі реєстру, відсутні цільові файли, невідомі принципали завдань,
   неперевірені метадані підписувача, історичні вирізані записи або тригер, який неможливо підтвердити.

Синтаксис команди, профілі, усі поля виводу та стани охоплення описано в
[посібнику з команди Persistence Hunter](../commands/persistence-hunter.md). У
[посібниках з артефактів](../artifacts/index.md) пояснено базові джерела, а в розділі
[Подяки](acknowledgements.md) наведено першоджерельні інструменти для виявлення закріплення.
