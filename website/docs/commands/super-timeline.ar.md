# سوبر الجدول الزمني { #super-timeline }

يقوم `super-timeline` بتحويل العناصر التي تم تحليلها إلى أحداث ذات مخطط مشترك وفرزها حسب الوقت. يمكن أن يحتوي سجل Prefetch على عدة مرات تنفيذ؛ يمكن أن يحتوي سجل MFT على ثمانية طوابع زمنية أو أكثر للملفات. ويصبح كل منها حدثًا يحمل علامة منفصلة. وهذا يجعل من السهل مقارنة الأدلة من مصادر مختلفة دون فقدان ما يعنيه كل طابع زمني فعليًا.

ابدأ بنتائج [`auto-parse`](auto-parse.md)، بدلاً من دليل الأدلة الأصلي:

```bash
juntei auto-parse -d evidence/ -o parsed/
juntei super-timeline -d parsed/ -o SuperTimeline.csv
```

الاحتفاظ بالملفات والبيانات والأدلة الأصلية التي تم تحليلها. الجدول الزمني هو إسقاط للتحليل. ولا يحل محل تلك السجلات أو ينشئ ملف تخزين Plaso أصلي.

## الاستخدام { #usage }

```bash
# Native CSV (default)
juntei super-timeline -d parsed/ -o SuperTimeline.csv

# Native JSON Lines
juntei super-timeline -d parsed/ -o SuperTimeline.jsonl -t jsonl

# Combine native records and an existing Hayabusa JSONL timeline
juntei super-timeline -f NativeRecords.jsonl --hayabusa Hayabusa.jsonl \
  -o SuperTimeline.jsonl -t jsonl

# Timesketch import profile; also available with CSV
juntei super-timeline -d parsed/ -o Timesketch.jsonl -t jsonl --profile timesketch

# One standalone CSV needs an artifact identifier and, if unavailable, a computer name
juntei super-timeline -f MFT.csv --input-artifact mft --computer HOST01 \
  -o Host01Timeline.csv

# Reduce the time range, memory used by sorting, or number of workers
juntei super-timeline -d parsed/ -o IncidentTimeline.jsonl -t jsonl \
  --timeline-start "2026-10-20T06:00:00Z" --timeline-end "2026-10-20T14:00:00Z" \
  --memory-limit 64 -T 4 --temp-dir scratch/
```

يمكن تكرار `--hayabusa FILE` أو استخدامه بمفرده. يقوم باستيراد الطوابع الزمنية للحدث/التنبيه الحالي وسياق القاعدة دون تشغيل Hayabusa. يتم دعم الأحداث المعلوماتية التي تكون `Details` عبارة عن سلسلة. يقيد `--artifact mft,prefetch` العرض على معرفات القطع الأثرية المحددة. الحدود الزمنية شاملة وتتطلب إزاحة UTC صريحة أو `Z`.

### اختيار المدخلات { #choosing-an-input }

| الإدخال | كيف يتم التعرف عليه |
|---|---|
| `-d DIR` | يوفر `manifest.json` المهام الأساسية الناجحة ومعرفات العناصر وأجهزة الكمبيوتر وملفات الإخراج الدقيقة. يتم استبعاد مهام `auto-parse -j` الثانوية لمنع استيراد كلا النسختين. |
| `-f FILE` | يستخدم JSON/JSONL الأصلي حقول `Artifact` و`Comp`. تحتاج الصادرات غير المميزة إلى `--input-artifact`؛ يتطلب CSV المستقل ذلك دائمًا. |
| `--computer NAME` | الإجراء الاحتياطي عندما لا يكون لسجل الإدخال اسم كمبيوتر؛ وإلا فإن الكمبيوتر غير المعروف هو `Unknown` بشكل صريح. |
| `--hayabusa FILE` | JSONL مع الطوابع الزمنية Hayabusa، وبيانات تعريف القاعدة، والكمبيوتر، و`EvtxFile`، في حالة وجودها. |

تدعم البيانات الحالية نقل الدليل الذي تم تحليله: يتم حل مسارات الإخراج المطلقة المسجلة ضمن الدليل الجديد. يجب أن تظل المدخلات بداخله، بما في ذلك أهداف الارتباط الرمزي. يتم دعم الدلائل القديمة لكل قطعة أثرية Amcache وSRUM وJump Lists؛ تحتاج أدلة الفئات إلى `OutputFiles` صريح.

يتم دعم البيانات الحالية ذات المسارات النسبية للمخرجات والصادرات المسطحة للجداول المتعددة. يتعرف الأمر على كل قطعة أثرية مجدولة عن طريق التحليل التلقائي، بما في ذلك المتصفح الأحدث وجداول WebCache وOutlook وUAL.

عندما يحدد البيان صورة VHDX أو E01، تتضمن مراجع المصدر الصورة والمسار الداخلي، ويتم الاحتفاظ باسم الصورة في سياق الحدث. ليست هناك حاجة إلى مساحة العمل المؤقتة لقراءة النتائج التي تم تحليلها.

يتم أخذ المصدر الخام من السجل أو أمر واضح لا لبس فيه. مع `-d`، ترتبط مراجع المصدر الأولي بدليل الأدلة، و`Details.ParsedFile` والملخص `InputFiles` مرتبطان بالدليل الذي تم تحليله. ترتبط أسماء المخرجات/التقارير الموجزة بدليل مخرجات المخطط الزمني. يتم تعيين جداول SRUM CSV إلى قاعدة بيانات فقط عندما يكون لدى المضيف ملف SRUDB.dat واحد يمكن التعرف عليه بشكل فريد. وإلا فإن `SourceFile` يشير إلى الملف الذي تم تحليله ويكون `Details.RawSourceAvailable` هو `false`.

تتم الإشارة إلى الإدخال المستقل بواسطة اسم الملف الخاص به. تستخدم المدخلات التي لها نفس اسم الملف مراجع `./Inputs/<ID>/<filename>` مميزة. تستخدم مسارات المصدر الخام المطلقة خارج جذور الأدلة المعروفة معرفات `./Sources/<ID>/<filename>`. تحتفظ هذه المراجع المبهمة بتمييزات المصدر دون تصدير أسماء الدليل المطلقة للمحلل؛ راجع السجل الأصلي باستخدام `ParsedFile` و`InputRecord` للمصدر الأصلي. تظل المسارات المسجلة في الدليل، مثل المسارات القابلة للتنفيذ Windows، دون تغيير.

## حقول الأحداث المشتركة { #common-event-fields }

| الميدان | معنى |
|---|---|
| `Timestamp` | UTC RFC 3339، مكتوب بتسعة أرقام كسرية لترتيب متسق. الحشو لا يضيف الدقة. |
| `Comp` | الكمبيوتر المرتبط بسجل الإدخال. |
| `Artifact` | معرف قطعة أثرية ثابت مثل `mft` أو `prefetch` أو `srum` أو `hayabusa`. |
| `TimestampType` | وصف معنى الطابع الزمني، مثل `MFT SI Data modified`. |
| `User` | الحساب المسجل أو SID عندما يكون لدى المحول واحد؛ قد تكون فارغة. |
| `Path` | الملف المتأثر أو مفتاح التسجيل أو أي كائن آخر خاص بالمنتج. |
| `Message` | وصف موجز لعارض الجدول الزمني. |
| `SourceFile` | مرجع المصدر الأولي النسبي للأدلة، أو معرف المصدر النسبي عندما يكون جذره غير معروف؛ وإلا فإن الإجراء الاحتياطي للملف الذي تم تحليله هو الموضح أعلاه. |
| `SourceField` | الحقل الذي تم تحليله بالضبط أو الموقع المتداخل المستخدم للطابع الزمني. |
| `RecordID` | هوية السجل الخاصة بالقطعة الأثرية. وهو ليس بالضرورة سجل EVTX ID. |
| `Details` | السياق المنظم بما في ذلك الطابع الزمني الأصلي والدقة والأساس الزمني ودور الوقت والملف المحلل وسجل الإدخال/الموقع وبيانات تعريف الاسترداد/القاعدة المتاحة. |

في CSV، `Details` عبارة عن خلية JSON مقتبسة. في JSONL هو كائن. يقوم ملف تعريف Timesketch بتغيير `Timestamp` و`TimestampType` و`Message` إلى `datetime` و`timestamp_desc` و`message`، على التوالي، مع الاحتفاظ بحقول المصدر الأخرى. هذه هي حقول استيراد Timesketch الثلاثة المطلوبة [](https://timesketch.org/guides/user/import-from-json-csv/).

يحتوي `Details` عمدًا على سياق محدد، بدلاً من البيانات الثنائية الكاملة أو كل حقل سجل أصلي. يتم تحديد السلاسل الطويلة والمصفوفات والكائنات ووضع علامة `ProjectionOmitted` عليها. ابحث عن `Details.ParsedFile` و`InputRecord` و`Location` لفحص السجل الأصلي الكامل. بالنسبة إلى CSV، يقوم رقم السجل بحساب سجلات CSV بعد الرأس، وليس الأسطر الفعلية داخل الخلايا المقتبسة. بالنسبة لـ JSONL فهو رقم السطر؛ بالنسبة إلى JSON، فهو رقم مستند المستوى الأعلى بالإضافة إلى الموقع المتداخل.

## ماذا تعني الأوقات { #what-the-times-mean }

الطابع الزمني هو دليل على كائن مسجل. وهو ليس في حد ذاته دليلاً على التنفيذ أو الهجوم. تحافظ المحولات عن عمد على هذه الفروق:

| التحف | تفسير الجدول الزمني |
|---|---|
| MFT | تعديل SI وFN بشكل منفصل، والوصول، وتغيير البيانات الوصفية، وأوقات الإنشاء؛ تظل السمات المسماة FN متميزة. يتم دمج حقول SI المتكررة في صفوف أسماء الملفات. يتم استبعاد أوقات الملف الأساسي المشترك لصفوف ADS. تحتفظ أسماء ركود سجلات FILE المستردة بأحداث FN المنفصلة. |
| I30 | بيانات تعريف FN/الفهرس المخزنة، مع سياق الركود/الاسترداد عندما يكون ذلك متاحًا. هذه ليست طوابع زمنية لكتابة فهرس الدليل. |
| مجلة USN | الطابع الزمني لتسجيل دفتر اليومية وأسباب التحديث. يمكن أن يصف السجل العديد من التغييرات؛ لا يسجل بالضرورة وقت البدء الدقيق. |
| LogFile | لقطات الطابع الزمني للإعادة/التراجع المخزنة وبيانات تعريف اسم الملف. تظل الإعادة والتراجع منفصلتين. تعد LSNs وإزاحات الملفات معرفات، ولا يتم تحويلها أبدًا إلى تواريخ. |
| Prefetch | أوقات التنفيذ المسجلة، مدمجة مع تصدير المخطط الزمني Prefetch المطابق. تتم تسمية البيانات التعريفية لإنشاء وحدة التخزين المشار إليها بشكل منفصل. |
| قواعد بيانات متصفح SQLite | الزيارات المسجلة، والبيانات الوصفية للزيارة الأخيرة للصفحة المستردة، وبدء/نهاية التنزيل، وإنشاء/الوصول/انتهاء صلاحية ملف تعريف الارتباط وسجل النموذج لأول/آخر استخدام أو شواهد القبور للحذف. لا تثبت نهاية التنزيل في حد ذاتها النجاح أو التنفيذ؛ انتهاء صلاحية ملف تعريف الارتباط هو موعد نهائي محدد. تظل حالة التعافي والثقة والأصل في السياق. |
| إنترنت إكسبلورر / ليجاسي إيدج WebCache | الوصول إلى الإدخال المخزن، والإنشاء/التعديل، وانتهاء الصلاحية والمزامنة، وبدء التنزيل، والبيانات التعريفية لملفات تعريف الارتباط، والوصول إلى/مسح الحاوية. لا يعد مسك الدفاتر في ذاكرة التخزين المؤقت دليلاً تلقائيًا على قيام المستخدم بفتح الصفحة. |
| توقعات PST، OST، MSG وOFT | إرسال/تسليم الرسالة؛ إنشاء/تعديل المجلد والعنصر والمرفقات؛ بداية/نهاية/تذكيرات التقويم؛ بدء المهمة/استحقاقها/اكتمالها/التذكيرات؛ وخصائص الوقت المكتوبة بشكل صريح. الأوقات المجدولة لا تثبت حدوث اجتماع أو إطلاق تذكير أو تنفيذ برنامج. لا يثبت وقت التسليم المخزن أنه تم قراءة الرسالة. |
| تسجيل وصول المستخدم (UAL) | البيانات التعريفية للوصول لأول/آخر مرة، وإدراج/إنشاء قاعدة البيانات، وأول/آخر ظهور ووقت تشغيل نظام التشغيل المُخزن. يظل الدور والحساب وعنوان المصدر والعدادات اليومية هو السياق. لا يتم اختراع التواريخ/الأعداد اليومية وعمليات تسجيل الدخول في منتصف الليل؛ تظل الهوية غير المحددة بالتوقيت وصفوف DNS متاحة في التقرير المصاحب. |
| Amcache | آخر عمليات كتابة لمفتاح المخزون وسياق مفتاح وحدة التخزين الأصلية وتواريخ التثبيت المسجلة وبيانات التعريف الخاصة برابط PE. وجود المخزون أو LinkDate وحده لا يثبت التنفيذ. |
| ShimCache | تعديل الملف المخزن، وبيانات التعريف لتحديث ذاكرة التخزين المؤقت، والكتابة الأخيرة لمفتاح ذاكرة التخزين المؤقت. لا شيء يعد طابعًا زمنيًا للتنفيذ تلقائيًا. |
| SRUM | الطابع الزمني/مجموعة الموفر، وبدء الاتصال، وحقول الفاصل الزمني للبداية/الانتهاء الصريحة، والبيانات التعريفية لمعرف التطبيق. البايتات والمدة والعدادات الأخرى ليست تواريخ. |
| LNK | الطوابع الزمنية المستهدفة MAC وإنشاء معرف التتبع وأوقات عناصر الصدفة. وهي تصف بيانات تعريف الهدف المخزنة، وليس بالضرورة عند فتح الاختصار. |
| Jump Lists | أدخل بيانات تعريف الاستخدام الأخير، وإنشاء معرف التتبع، والأوقات المستهدفة LNK. يحذف الإعداد الافتراضي أوقات ملفات الحاوية من جانب المجموعة. |
| Defender الحجر الصحي | الطابع الزمني للإدخال وأوقات إنشاء/الوصول/الكتابة للموارد المخزنة. أوقات الاستخراج ليست دليلاً على نشاط نقطة النهاية. |
| BAM, UserAssist, FeatureUsage | حقول النشاط المسجلة حيثما تكون موجودة، مع الحفاظ على سياق الكتابة الأخيرة الرئيسي مميزًا. العداد بدون وقت لا يخلق حدثا. |
| RecentDocs، MRU، فتح/حفظ MRU، ShellBags، المكتب | أوقات الاستخدام/الثقة/عناصر الصدفة المسجلة والسياق الرئيسي. الوقت الرئيسي للقائمة ليس هو وقت الاستخدام الأخير الفردي لكل عنصر في القائمة. |
| أسرار SAM وLSA | تسجيل الدخول إلى الحساب/كلمة المرور/انتهاء الصلاحية أو البيانات التعريفية السرية وأوقات المفاتيح ذات الصلة. ولا تحل هذه محل سجلات أحداث المصادقة. |
| الخدمات، TaskCache، استمرارية التسجيل، BCD | البيانات التعريفية للمفتاح/التكوين وأوقات المهام المسجلة بشكل صريح. لا تثبت عمليات كتابة مفتاح الخدمة وحدها تنفيذ الخدمة. |
| الشبكات وUSB | حقول ملف تعريف الشبكة/التأجير وتثبيت الجهاز/الوصول/الإزالة، مع سياق مفتاح التسجيل. يحتفظ مستخدم USB الأصلي MountPoints2 بمصدر خلية المستخدم المقابل. |
| معلومات النظام، البرامج المثبتة، AppCompat، تاريخ التطبيق | التثبيت الصريح، وإيقاف التشغيل، والمخزون/النشاط، وحقول البيانات الوصفية الرئيسية. تحتفظ صفائف ملف تعريف/إصدار معلومات النظام الأصلية بأوقاتها المتداخلة. |
| سياسة التدقيق، إعدادات الأمان، MuiCache، التسجيل العام | مفتاح أوقات الكتابة الأخيرة عند توفيره؛ تظل القيم/العدادات غير المحددة متاحة في الإدخال الأصلي. |
| Persistence Hunter | دعم مفتاح الكتابة الأخيرة ووقت التغيير المرتبط. النتيجة ليست في حد ذاتها تثبيتًا ذو طابع زمني أو حكمًا بالتسوية. |
| Hayabusa | الطابع الزمني للحدث/التنبيه مع القاعدة والمستوى والقناة والحدث ID وسياق التفاصيل المتاح. تظل القواعد المتعددة وصفوف الارتباط المميزة منفصلة. |

يتم الاحتفاظ بطوابع زمنية متعددة متساوية ذات معاني أو مصادر أدلة مختلفة. تتضمن الهوية المكررة الكمبيوتر والمصدر والقطعة الأثرية والسجل ومعنى الوقت وحالة الاسترداد. تسجل الصفوف المدمجة `DuplicateCount` والمسارات البديلة/حقول المصدر المحدودة. لا يتم دمج المصادر المميزة أبدًا لمجرد أن مساراتها وطوابعها الزمنية متشابهة. عندما لا يمكن حل المصدر الأولي، يتم الاحتفاظ بهوية سجل الإدخال لتجنب طي اللقطات المختلفة.

### الدقة والتوقيت المحلي والافتراضات { #precision-local-times-and-assumptions }

تتم تسوية حقول UTC المعروفة والطوابع الزمنية ذات الإزاحات الصريحة إلى UTC. يتم الاحتفاظ بالقيم الأصلية ودقتها المسجلة، بما في ذلك 100 ns FILETIMEs. قد يكون المحلل اللغوي المصدر أو العارض النهائي قد قام بالفعل بتقريب الوقت؛ لا يمكن لهذا الأمر استعادة الدقة المفقودة.

تحتوي بعض حقول عنصر الصدفة/FAT على دلالات بالتوقيت المحلي حتى عندما يقوم المحلل اللغوي الرئيسي بتسلسلها باستخدام `Z`. يحافظ المخطط الزمني على القيمة التي تم تحليلها وأصل الحقل؛ ولا يمكنه استرداد المنطقة الزمنية المفقودة لنقطة النهاية أو التحقق من صحة التحويل الأولي. تحقق من العناصر الأولية وإعدادات نقطة النهاية قبل استخدام مثل هذا الوقت للارتباط الدقيق بين المضيفين.

يتم تشخيص طابع زمني ساذج بدون منطقة زمنية محددة، بدلاً من معاملته بصمت على أنه UTC. إذا كان الدليل يبرر ذلك، قم بتقديم إزاحة ثابتة موقعة:

```bash
juntei super-timeline -f Amcache.jsonl --input-artifact amcache \
  --assume-offset "+09:00" -o Timeline.csv
```

تتطلب قيم التاريخ فقط هذا الخيار أيضًا. تم تصنيف مرساة منتصف الليل الخاصة بهم على أنها افتراض بدقة **اليوم** ؛ إنه ليس حدث منتصف الليل الملحوظ. لا يتم قبول أسماء المناطق الزمنية وقواعد التوقيت الصيفي. لا تؤدي القيم المفقودة والصفرية وغير الصالحة والخارجة عن النطاق إلى إنتاج أحداث حقبة تركيبية. يتم الاحتفاظ بتاريخ 1970 صالح ومسجل بشكل صريح.

يتم استبعاد فئتين اختياريتين بشكل افتراضي:

- `--include-collection-times`: LNK/Jump List بيانات تعريف الملف المصدر في نظام ملفات التجميع/التحليل. يتم تسمية هذه الأحداث باسم `collection_filesystem`، وهي منفصلة عن نشاط نقطة النهاية.
- `--include-interpreted-times`: قيم التسجيل العامة QWORD التي يتم تقديمها كـ FILETIME بواسطة قارئ التسجيل. يتم تسميتها بـ `interpreted_value` لأن العديد من هذه القيم هي في الواقع عدادات.

## تقارير مصاحبة { #companion-reports }

بالنسبة إلى `SuperTimeline.csv`، يكتب الأمر أيضًا:

- `SuperTimeline.csv-Untimed.jsonl`: مواقع التسجيل الأصلية بدون طابع زمني قابل للاستخدام للحدث.
- `SuperTimeline.csv-Diagnostics.jsonl`: أوقات غير صالحة/غامضة، تم تخطي بيانات التعريف المشتركة وقيود الدقة التي تتطلب السجل الأصلي الذي تم تحليله عمدًا.
- `SuperTimeline.csv-Summary.json`: ملفات الإدخال، وعدد كل قطعة أثرية، والأحداث التي تمت تصفيتها/المرشح/المجمعة، وعدد المخرجات، والعاملون، وفرز الميزانية/القطع/التمريرات والوقت المنقضي.

تتضمن الأسماء المصاحبة اسم ملف الإخراج الكامل. على سبيل المثال، يحتوي `SuperTimeline.jsonl` على `SuperTimeline.jsonl-Summary.json` الخاص به والتقارير التشخيصية/غير المحددة بوقت المقابلة. يمكن أن تتعايش صادرات CSV وJSONL بنفس الجذع؛ `-C` مطلوب فقط لاستبدال مجموعة النتائج الموجودة.

التواريخ الصالحة التي تنتظر منطقة زمنية محددة تزيد `UnresolvedTimeZones`، بدلاً من `InvalidTimestamps`. كلاهما يظل قابلاً للتتبع في التشخيص. لم يتم اختراع أي طابع زمني.

يتم احتساب السجلات ذات الأوقات الصالحة خارج النطاق المطلوب على أنها تمت تصفيتها، وليس غير محددة التوقيت. تسبق أعداد الأحداث المرشحة الدمج المكرر. يعني `Complete: true` أن جميع المدخلات التي تم تحليلها قد تمت معالجتها بنجاح؛ هذا لا يعني أنه تم جمع كل قطعة أثرية، أو أن كل حقل له طابع زمني، أو أنه يمكن اكتشاف كل هجوم.

يمكن لصادرات CSV تسوية بيانات التعريف المتداخلة: يمكن أن تكون ملفات تعريف معلومات النظام ونقاط تثبيت المستخدم USB وعناصر الصدفة والسياق المنظم الآخر أكثر ثراءً في JSON/JSONL الأصلي. استخدم الإدخال الأصلي عندما تكون هذه الحقول مهمة. لا يمكن للمخطط الزمني إعادة بناء البيانات المحذوفة بواسطة تصدير CSV. تتسبب معرفات العناصر غير المدعومة وملفات الإدخال المشوهة في حدوث خطأ بدلاً من نجاح يحتوي على نتائج جزئية.

## سلامة الأداء والمخرجات { #performance-and-output-safety }

يتم دفق المدخلات ومعالجتها بالتوازي. تتسرب مخازن الفرز المؤقتة إلى دليل مؤقت خاص، ثم تنتج تمريرات الدمج المحدودة مخرجات زمنية محددة. يستخدم الفرز عددًا صحيحًا كاملاً من الثواني والنانو ثانية، بما في ذلك التواريخ قبل 1970. يعد الترتيب في الوقت المتساوي أمرًا حتميًا عبر أعداد العمال وفرز الميزانيات.

`--memory-limit` هو إجمالي **ميزانية المخزن المؤقت للفرز**، وليس حد RSS للعملية. تتطلب سجلات الإدخال، والكائنات/السلسلة JSON، والمخازن المؤقتة CSV، وسجلات الدمج ذاكرة إضافية. يتم تقليل عدد العمال للميزانيات الصغيرة. يحدد `--max-record-size` سجل الإدخال الذي تم تحليله (الافتراضي 16 MiB)؛ يتم احتساب صفيف/تقرير JSON الجميل كمستند إدخال واحد عالي المستوى. قد تحتاج المستندات الأكبر حجمًا إلى حد أعلى، أو يفضل JSONL. تساهم القراءة المسبقة لمحلل CSV أيضًا في تحقيق هذا الحد.

يجب أن تستوعب مساحة القرص المؤقتة الأحداث الموسعة وتمريرات الدمج، بالإضافة إلى النتائج النهائية. يمكن أن ينتج عن السجل العديد من الأحداث، لذلك يمكن أن يكون المخطط الزمني أكبر بكثير من الإدخال. قم بتصفية النطاق الزمني/العناصر الأثرية عندما يكون ذلك مناسبًا وحدد وحدة تخزين مؤقتة بمساحة خالية كافية.

يقوم Ctrl+C بالإلغاء بشكل تعاوني، ويزيل أدلة الفرز/التدريج الخاصة ويخرج بالرمز `130`. في Linux وmacOS، ينطبق هذا أيضًا على SIGTERM وSIGHUP. يتم التحقق من الإلغاء أثناء قراءة التقارير وتطبيعها ودمجها وكتابتها، قبل بدء النشر. لا يزال من الممكن أن يؤدي الإنهاء غير القابل للإصلاح أو فقدان الطاقة إلى ترك ملفات مؤقتة.

تتطلب المخرجات الحالية `-C`. يجب ألا يحل الجدول الزمني والمرافق محل المدخلات أو البيانات أو الأدلة المحلية المشار إليها أو أدلة الأدلة المحمية الخاصة بها. أخطاء الإدخال أو فشل الفرز تترك المخرجات الموجودة دون تغيير. يتم تنظيم الملفات المكتملة بجانب الوجهة واستبدالها بشكل فردي، مع نشر المخطط الزمني أخيرًا. هذه **ليست** معاملة عبر الملفات الأربعة: قد يؤدي فشل الإدخال/الإخراج أثناء النشر النهائي إلى استبدال بعض التقارير المصاحبة. احتفظ بالاسم الأساسي الجديد للمخرجات لكل عملية تشغيل عندما يكون الاحتفاظ بتصدير كامل سابق أمرًا مهمًا.

## أحدث موزعي الجداول المتعددة { #newer-multi-table-parsers }

يحمل JSON/JSONL الأصلي اسم كل جدول. بالنسبة إلى CSV المستقل، يقوم المتصفح ومحولات WebCache وOutlook بتعريف الجدول الخاص به من مخطط العمود، لذا فإن إعادة تسمية CSV أو استخدام لاحقات مصدر التحليل التلقائي لا يغير تفسير الطابع الزمني. يحتفظ UAL بحقول الطابع الزمني المعروفة الصريحة؛ لا يتم تخمين عدادات الوصول والنصوص غير المرتبطة بالتاريخ كتواريخ.

يتم عرض صفوف خصائص Outlook فقط عندما يكون نوعها المُعلن هو نوع زمني أو متعدد الأوقات. تظل السلسلة التي تحتوي على تاريخ سلسلة. تحتفظ الرسائل المضمنة بمعرفات العناصر والمراجع الأصلية، ولا يتم استبدال أوقات استخراج المرفقات بالطوابع الزمنية للمرفقات المخزنة. تظل صفوف الملفات أو المستلمين أو جهات الاتصال أو الخصائص غير المحددة قابلة للتتبع في الإخراج الأصلي والتقرير غير المحدد بوقت.

تنطبق نفس مخططات الإخراج CSV وJSONL على هؤلاء المحللين؛ لا تؤدي إضافة قطعة أثرية جديدة إلى إضافة مئات من أعمدة CSV. يبقى السياق الخاص بالمنتج في `Details`.
