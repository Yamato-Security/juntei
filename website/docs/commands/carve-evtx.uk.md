# Вирізання журналів подій { #carve-evtx }

Відновлення блоків журналів подій, що залишилися після очищення або видалення журналу: з образу диска, нерозподіленого простору, файлу підкачки або образу пам'яті. Кожен блок (chunk) EVTX розміром 64 КіБ містить власні таблиці рядків і шаблонів, тому його записи можна прочитати без решти журналу. Juntei записує відновлені блоки як звичайні файли `.evtx`, по одному на канал, для Hayabusa або «Переглядача подій».

```bash
juntei carve-evtx -f host.E01 -o carved/
juntei carve-evtx -f host.vhdx --free-space-only -o carved-free/
juntei carve-evtx -f pagefile.sys --live-logs evidence/C/Windows/System32/winevt/Logs/ -o carved-pagefile/
juntei carve-evtx -f memory.raw -o carved-memory/ -t jsonl
```

Без `-o` виводиться лише підсумок.

## Пошук блоків { #finding-chunks }

- Сигнатура блоку шукається з кожного зміщення байта, і кожен заголовок має бути правдоподібним (розмір заголовка, номери записів, зміщення). Контрольні суми повідомляються, але не є обов'язковими: частково перезаписаний блок усе ще містить записи, які можна прочитати.
- Блоки журналів зі стисненням NTFS розпаковуються (LZNT1, одиниці по 16 кластерів). Для образу диска використовується розмір кластера тому; для інших файлів — `--cluster-size <BYTES>` (типово 4096).
- Записи обходяться за їхнім розміром до зміщення останнього запису, зазначеного в заголовку, і повторюваний ідентифікатор запису ніколи не зупиняє обхід. Після пошкодженого запису обхід продовжується з наступного дійсного запису. Старі записи в slack блоку також перелічуються.

## Образи дисків і томи NTFS { #disk-images }

Для образу E01 або VHDX, а також для сирого диска чи тому з NTFS кожен блок класифікується за кластером, у якому він лежить:

| Розташування | Значення |
|---|---|
| `FreeSpace` | Кластер, який не використовує жоден файл. |
| `DeletedLog` | Вільний кластер, який досі перелічує запис `$MFT` видаленого журналу, або журнал, відновлений із таких кластерів. |
| `LiveLog` | Кластер журналу подій, що використовується. Пропускається, якщо не вказано `--keep-live`. |
| `AllocatedFile` | Кластер іншого файлу, наприклад `pagefile.sys` або файлу сховища тіньової копії. |
| `AllocatedUnknown` | Розподілений кластер, якого не перелічує жоден запис `$MFT`. |
| `OutsideVolumes` | Поза всіма томами NTFS диска. |
| `Unclassified` | Вхідні дані не містять тому NTFS (файл підкачки або образ пам'яті). |

Видалені журнали, запис `$MFT` яких перелічує лише вільні кластери, відновлюються повністю, зокрема й стиснені, і зберігаються в `Recovered/`. `--free-space-only` шукає лише у вільних кластерах: так швидше, але файл підкачки, тіньові копії та інші файли пропускаються.

## Дедуплікація { #deduplication }

Кожен блок записується один раз. Блок пропускається, якщо він належить активному журналу, якщо він ідентичний іншому блоку або якщо всі його записи вже є в активних журналах чи в уже записаному блоці. Блоки з більшою кількістю записів розглядаються першими, тому старіша, коротша копія блоку нічого не додає. Для вхідних даних без NTFS вкажіть активні журнали за допомогою `--live-logs <DIR>`.

## Результати { #results }

- `Carved/<CHANNEL>.evtx`: один журнал на канал з іменем за правилами Windows (`Microsoft-Windows-Sysmon%4Operational.evtx`). Номери записів у заголовках блоків перенумеровуються, а контрольні суми перераховуються. Пошкоджений запис і все, що йде після нього, стають slack. В іншому кожен блок зберігається повністю, разом зі своїм slack, тому відновлення записів, як-от `-x` у Hayabusa, на ньому й надалі працює. Параметр `-x` у Hayabusa шукає записи в блоках, позначених як порожні. Записи у вільній частині частково заповнених блоків можна знайти у файлі `records.csv` Juntei.
- `Recovered/Volume<N>/...`: видалені журнали, відновлені з їхніх записів `$MFT`.
- `chunks.csv` / `chunks.jsonl`: усі знайдені блоки: де кожен був, що з ним сталося (`Status`), його канал, ідентифікатори записів, часи та стан контрольної суми.
- `records.csv` / `records.jsonl`: усі записи записаних блоків. `OnlyInCarvedData` позначає записи, яких немає в активних журналах.

```bash
hayabusa csv-timeline -d carved/Carved -a -o carved-timeline.csv
```

Вирізання знаходить лише суцільні блоки. Блок, розділений між несуміжними кластерами або несуміжними фізичними сторінками пам'яті, неповний, і його пізніші записи можуть бути пошкоджені або відсутні. Спершу розпакуйте `hiberfil.sys`. Код виходу — 0, якщо пошук завершено, і 1 у разі помилки.
