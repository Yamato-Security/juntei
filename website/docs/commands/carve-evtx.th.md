# การกู้คืนล็อกเหตุการณ์แบบ carving { #carve-evtx }

กู้คืนชังก์ (chunk) ของล็อกเหตุการณ์ที่ยังหลงเหลืออยู่หลังจากล็อกถูกล้างหรือถูกลบไปแล้ว จากอิมเมจดิสก์ พื้นที่ที่ไม่ได้จัดสรร ไฟล์เพจ หรืออิมเมจหน่วยความจำ ชังก์ EVTX ขนาด 64 KiB แต่ละชังก์มีตารางสตริงและตารางเทมเพลตของตัวเอง จึงอ่านเรคคอร์ดในชังก์ได้แม้ไม่มีส่วนอื่นของล็อก Juntei เขียนชังก์ที่กู้คืนได้เป็นไฟล์ `.evtx` ปกติ แยกหนึ่งไฟล์ต่อหนึ่งแชนเนล เพื่อนำไปเปิดด้วย Hayabusa หรือ Event Viewer

```bash
juntei carve-evtx -f host.E01 -o carved/
juntei carve-evtx -f host.vhdx --free-space-only -o carved-free/
juntei carve-evtx -f pagefile.sys --live-logs evidence/C/Windows/System32/winevt/Logs/ -o carved-pagefile/
juntei carve-evtx -f memory.raw -o carved-memory/ -t jsonl
```

หากไม่ระบุ `-o` จะแสดงเฉพาะสรุปผล

## การค้นหาชังก์ { #finding-chunks }

- ค้นหาลายเซ็นของชังก์ที่ทุก offset ระดับไบต์ และส่วนหัวของแต่ละชังก์ต้องมีค่าที่สมเหตุสมผล (ขนาดส่วนหัว หมายเลขเรคคอร์ด offset) ส่วน checksum จะถูกรายงานแต่ไม่ได้บังคับว่าต้องถูกต้อง เพราะชังก์ที่ถูกเขียนทับไปบางส่วนก็ยังมีเรคคอร์ดที่อ่านได้
- ชังก์ของล็อกที่ถูกบีบอัดด้วย NTFS จะถูกคลายการบีบอัด (LZNT1 หน่วยละ 16 คลัสเตอร์) สำหรับอิมเมจดิสก์จะใช้ขนาดคลัสเตอร์ของวอลุ่ม ส่วนไฟล์อื่นจะใช้ `--cluster-size <BYTES>` (ค่าเริ่มต้น 4096)
- อ่านเรคคอร์ดไล่ตามขนาดไปจนถึง offset ของเรคคอร์ดสุดท้ายที่ระบุในส่วนหัว และไม่หยุดเพียงเพราะพบ ID เรคคอร์ดซ้ำ เมื่อเจอเรคคอร์ดที่เสียหาย จะอ่านต่อจากเรคคอร์ดถัดไปที่ถูกต้อง เรคคอร์ดเก่าที่อยู่ใน slack ของชังก์ก็จะถูกแสดงด้วย

## อิมเมจดิสก์และวอลุ่ม NTFS { #disk-images }

สำหรับอิมเมจ E01 หรือ VHDX หรือดิสก์หรือวอลุ่มแบบ raw ที่มี NTFS ทุกชังก์จะถูกจัดประเภทตามคลัสเตอร์ที่ชังก์นั้นอยู่

| ตำแหน่ง | ความหมาย |
|---|---|
| `FreeSpace` | คลัสเตอร์ที่ไม่มีไฟล์ใดใช้งาน |
| `DeletedLog` | คลัสเตอร์ว่างที่เรคคอร์ด `$MFT` ของล็อกที่ถูกลบยังคงระบุไว้ หรือล็อกที่สร้างขึ้นใหม่จากคลัสเตอร์เหล่านั้น |
| `LiveLog` | คลัสเตอร์ของล็อกเหตุการณ์ที่กำลังใช้งานอยู่ จะไม่ถูกเขียนออกเว้นแต่ระบุ `--keep-live` |
| `AllocatedFile` | คลัสเตอร์ของไฟล์อื่น เช่น `pagefile.sys` หรือไฟล์ store ของ Volume Shadow Copy |
| `AllocatedUnknown` | คลัสเตอร์ที่จัดสรรแล้วแต่ไม่มีเรคคอร์ด `$MFT` ใดระบุไว้ |
| `OutsideVolumes` | อยู่นอกวอลุ่ม NTFS ทุกวอลุ่มของดิสก์ |
| `Unclassified` | อินพุตไม่มีวอลุ่ม NTFS (ไฟล์เพจหรืออิมเมจหน่วยความจำ) |

ล็อกที่ถูกลบซึ่งเรคคอร์ด `$MFT` ระบุไว้เฉพาะคลัสเตอร์ว่างจะถูกสร้างขึ้นใหม่ทั้งไฟล์ รวมถึงล็อกที่ถูกบีบอัด และบันทึกไว้ใต้ `Recovered/` ส่วน `--free-space-only` จะค้นหาเฉพาะคลัสเตอร์ว่าง ซึ่งเร็วกว่า แต่จะข้ามไฟล์เพจ Volume Shadow Copy และไฟล์อื่น ๆ

## การขจัดข้อมูลซ้ำ { #deduplication }

แต่ละชังก์จะถูกเขียนเพียงครั้งเดียว ชังก์จะถูกตัดออกเมื่อเป็นของล็อกที่ใช้งานอยู่ เมื่อเหมือนกับชังก์อื่นทุกประการ หรือเมื่อเรคคอร์ดทั้งหมดของชังก์มีอยู่แล้วในล็อกที่ใช้งานอยู่หรือในชังก์ที่เขียนไปแล้ว ชังก์ที่มีเรคคอร์ดมากกว่าจะได้รับการพิจารณาก่อน สำเนาของชังก์เดียวกันที่เก่าและสั้นกว่าจึงไม่เพิ่มอะไรใหม่ สำหรับอินพุตที่ไม่มี NTFS ให้ระบุล็อกที่ใช้งานอยู่ด้วย `--live-logs <DIR>`

## ผลลัพธ์ { #results }

- `Carved/<CHANNEL>.evtx`: ล็อกหนึ่งไฟล์ต่อหนึ่งแชนเนล ตั้งชื่อแบบเดียวกับที่ Windows ตั้งชื่อล็อก (`Microsoft-Windows-Sysmon%4Operational.evtx`) หมายเลขเรคคอร์ดในส่วนหัวของชังก์จะถูกกำหนดใหม่ และคำนวณ checksum ใหม่ เรคคอร์ดที่เสียหายและทุกอย่างที่อยู่หลังจากนั้นจะกลายเป็น slack นอกจากนั้นแต่ละชังก์จะถูกเก็บไว้ครบถ้วนรวมถึง slack ตัวเลือก `-x` ของ Hayabusa จะค้นหาในชังก์ที่ถูกระบุว่าว่าง สำหรับเรคคอร์ดที่ยังเหลือในพื้นที่ slack ของชังก์ที่ใช้งานอยู่บางส่วน ให้ดูไฟล์ `records.csv` ของ Juntei
- `Recovered/Volume<N>/...`: ล็อกที่ถูกลบซึ่งสร้างขึ้นใหม่จากเรคคอร์ด `$MFT`
- `chunks.csv` / `chunks.jsonl`: ทุกชังก์ที่พบ พร้อมตำแหน่งที่พบ ผลการจัดการ (`Status`) แชนเนล ID เรคคอร์ด เวลา และสถานะ checksum
- `records.csv` / `records.jsonl`: ทุกเรคคอร์ดของชังก์ที่ถูกเขียน `OnlyInCarvedData` ระบุเรคคอร์ดที่ไม่มีอยู่ในล็อกที่ใช้งานอยู่

```bash
hayabusa csv-timeline -d carved/Carved -a -o carved-timeline.csv
```

การ carving พบได้เฉพาะชังก์ที่อยู่ต่อเนื่องกันเท่านั้น ชังก์ที่ถูกแบ่งอยู่ในคลัสเตอร์ที่ไม่ต่อเนื่องกัน หรือในเพจกายภาพที่ไม่ต่อเนื่องกันในหน่วยความจำ จะไม่สมบูรณ์ และเรคคอร์ดช่วงหลังอาจเสียหายหรือหายไป ให้คลายการบีบอัด `hiberfil.sys` ก่อน รหัสออกเป็น 0 เมื่อการค้นหาเสร็จสมบูรณ์ และเป็น 1 เมื่อเกิดข้อผิดพลาด
