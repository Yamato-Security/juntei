# Changes

## 1.1.0 [xxxx/xx/xx]

**New Features:**

- `auto-parse --vhdx` reads images natively on Linux, macOS and Windows without FUSE, an OS mount, or administrator privileges. Files are staged in a private workspace on the output filesystem by default; `--temp-dir` selects an existing directory outside the output. Reserve space for copies and results. Keep original source metadata separately, retain readable results if staging fills, report failed writes once, and mark images that were not staged in both manifests. Skip inaccessible discovery subdirectories while treating an unreadable input root as an error. Ctrl+C, and SIGTERM/SIGHUP on Linux and macOS, stop and reap parser processes before removing staged evidence and return exit code 130. SIGKILL or power loss can leave copies. Preserve image provenance and keep private workspace paths out of exported results. (@YamatoSecurity)

- Use Yamato Security’s [ys-vhdx-parser](https://github.com/Yamato-Security/ys-vhdx-parser) workspace for the VHDX reader and reusable NTFS/FUSE mounting library, retaining the original reader’s license and attribution. (@YamatoSecurity)

- `parse-ese ual` parses the User Access Logging (UAL) databases of Windows Server (`Current.mdb`, the yearly `{GUID}.mdb` databases and `SystemIdentity.mdb`): the client addresses and accounts that used each server role, with their first and last access times and request counts per day, and the role, DNS, virtual machine and server identity tables. Results are CSV tables, JSON or JSONL. `auto-parse` saves them in `LateralMovement` and adds them to the `-j` timeline. (#133) (@YamatoSecurity)

- `parse-sqlite browser` parses web browser databases with Yamato Security's [ys-browser-parser](https://github.com/Yamato-Security/ys-browser-parser): the visits and downloads of Chromium-based browsers' `History` and Firefox's `places.sqlite`, the cookies of `Cookies` and `cookies.sqlite`, and the form history of `Web Data` and `formhistory.sqlite`. Each database is read with its `-wal` file, and deleted visits, pages, downloads and form entries are recovered and marked with where they were found. The browser, Windows user and profile come from each database's path. A time outside the years 0000–9999 is written as an empty CSV cell or JSON `null`. Results are CSV tables, JSON or JSONL. `auto-parse` saves them in the new `BrowserActivity` category and adds them to the `-j` timeline. (#104) (@YamatoSecurity)

- `parse-ese webcache` parses Internet Explorer and legacy Edge's `WebCacheV01.dat` with [ys-browser-parser](https://github.com/Yamato-Security/ys-browser-parser): the history (with page titles and all the entries' times, and the local files File Explorer opened), the downloads (where each file was saved, its size, start, referring page and MIME type or publisher), the cookies of Windows 10 and later, the cached files with their path and HTTP headers, cookie files, web storage and the containers. The Windows user comes from each database's path, and the app package from `AppData\Local\Packages` in each container's directory. A time outside the years 0000–9999 is written as an empty CSV cell or JSON `null`, as in `parse-sqlite browser`. Results are CSV tables, JSON or JSONL. `auto-parse` saves them in `BrowserActivity` and adds them to the `-j` timeline. (#104) (@YamatoSecurity)

- `parse-file outlook` parses Outlook's PST and OST stores (ANSI and Unicode PSTs, and OSTs, including those of Outlook 2013 and later) and `.msg` and `.oft` files with Yamato Security's [ys-outlook-parser](https://github.com/Yamato-Security/ys-outlook-parser): the stores and their folders, every item with its senders, recipients, times, categories and the beginning of its body, the hidden items of the folders, the items embedded in attachments at every level, the attachments with their SHA-256, and the fields of contacts, calendar items and tasks. `--properties` adds every property as stored, and `--extract-attachments` writes each attachment's data once, named by its SHA-256. Files are told apart by their contents, read leniently with the damage reported, and stores are written item by item, never held in memory whole. The Windows user comes from each file's path. Results are CSV tables, JSON or JSONL. `auto-parse` saves them in the new `Communication` category and adds them to the `-j` timeline. (#138) (@YamatoSecurity)

- `mount` mounts the NTFS volumes of a VHDX disk image read-only at a directory through FUSE (Linux), without root and without the system supporting the image or the file system, so other tools such as Hayabusa can read the files. NTFS volumes whose boot sectors have zeroed jump instructions and signatures are supported. Ctrl+C unmounts. (@YamatoSecurity)


- `auto-parse --e01` reads physical E01/Ex01 images natively on Linux, macOS and Windows without FUSE, OS mounting or administrator privileges. Split images start at their first segment; whole disks and single NTFS volumes use the same read-only temporary-workspace pipeline as VHDX. `--vhdx --e01` accepts mixed input, and the separate Linux/FUSE `mount` command also accepts E01 images. Uses [ys-e01-parser](https://github.com/Yamato-Security/ys-e01-parser), a reader-only fork of [ewf-image](https://github.com/ebrig/ewf-image). (#140) (@YamatoSecurity)

- `parse-registry muicache`: the programs users ran, with the names and companies Windows read from their version resources, from `MuiCache` in `UsrClass.dat` (Windows Vista and later) and `NTUSER.DAT` (Windows XP) hives, with ys-registry-parser: one record per program with its path, friendly app name and company (`<path>.FriendlyAppName` and `<path>.ApplicationCompany` joined on Windows 8 and later; `<path>` on Windows XP and 7), the key and its last-write time, and the user's name and SID (from the `UsrClass.dat`'s root key or the system's `ProfileList`). `LangID` and the shell's cached resource strings (`@<file>,-<number>`) are left out; values that aren't clean text keep their bytes. - `parse-registry bam`: when each user last ran each program, as the Background and Desktop Activity Moderators recorded it in `SYSTEM` hives, with ys-registry-parser: one record per value of each user's key under `Services\bam` and `Services\dam`, in both layouts (`State\UserSettings`, Windows 10 1809 and later, and `UserSettings`, 1709 to 1803): the program as Windows wrote it (a device path or a packaged app's ID), the device and the path on it, and the time it last ran; the user's SID and name, from the system's `SAM` (local accounts, by the computer's SID), its `ProfileList` (profile folders) or the well-known SIDs, with where the name comes from.
